## Migration lifecycle

PyCRMKit now ships a Django-owned migration history for the Django adapter.

```bash
python manage.py migrate pycrmkit_crm
```

Migrations are explicit deployment operations. Package import and application
startup do not mutate the database schema.

## Transaction bridge

```python
from pycrmkit.integrations.django.transactions import DjangoTransactionBridge

with DjangoTransactionBridge() as bridge:
    bridge.contacts.save(contact)
    bridge.organizations.save(organization)
    bridge.commit()
```

The bridge implements explicit transaction intent:

```text
commit()                 → persist
exit without commit      → rollback
exception                → rollback
rollback()               → discard current work and reopen
```

When used inside an ambient Django transaction, `bridge.commit()` only
releases its internal savepoint. Domain events wait for the actual outer
commit through Django's `on_commit` mechanism.

## Scope boundary

This beta exposes transactions for the Django repositories currently
implemented:

```text
Contact
Organization
Relationship
```

It is not yet the complete cross-domain PyCRMKit `UnitOfWork`. That
distinction prevents the framework from claiming adapter conformance that the
current implementation has not yet proven.

## Admin

Django admin autodiscovery registers operational views for:

```text
ContactModel
OrganizationModel
RelationshipModel
```

with contact and organization child rows available as inlines.

Admin is an infrastructure interface, not a replacement for PyCRMKit domain
services.
