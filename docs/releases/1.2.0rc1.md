## Purpose

This release is a **qualification of the existing Campaign 1.2 feature line**, not a new marketing product. It freezes public contracts and validates the production-relevant boundaries introduced in `1.2.0a1–1.2.0b3`:

- Campaign metadata, lifecycle and optimistic-revision updates;
- direct membership and deduplicated audience union with captured static/dynamic Segment sources;
- attribution references and links to existing CommunicationRecord **metadata**, never message-body delivery;
- optional FastAPI and DRF Campaign HTTP integration behind an **explicit host-authenticated** action/resource/scope policy;
- bounded direct-member import and paginated direct/audience/source CSV/JSON/JSONL export;
- Memory, SQLAlchemy/PostgreSQL and Django persistence, with their respective migration chains.

No domain-level API expansion, new storage migration, or unreviewed breaking change is intended in RC1.

## Integration and security boundary

A Campaign HTTP host must install and explicitly configure `CampaignHTTPAccess` with `CampaignSecurityBoundary`; the library does not ship a tenant directory, identity provider, JWT/OIDC validator or enforce third-party entity tenancy on every generic CRM route. Authentication is derived from a verified host principal, not an untrusted `X-Actor-ID` request header. Real host deployments require IAM, trusted tenant ownership, rate-limiting, audit/PII safeguards, database TLS, key rotation, and secrets management.

A separate sample in `examples/campaign_rc_host/` runs a signed synthetic tenant policy against real PostgreSQL 17 from a wheel-installed package. It explicitly denies dangerous generic mutation routes and re-creates the Engine/CRM to verify persistence. Its HMAC tokens, identity mapping and CI-only PostgreSQL trust service are **non-production fixtures**.

The Campaign package is not a marketing delivery engine. CommunicationRecord linkage stores references; it is not proof of email delivery. Database migration authority must remain separate for Django ORM versus Alembic/SQLAlchemy physical schemas.

## Import/export limitations

- Import accepts up to 1,000 direct-member rows. Per-row successful commits may survive a later error; **not** one atomic batch. Replays are idempotent for existing **direct** membership, not Segment-derived capture.
- Audience is deduplicated across direct and captured references. Captured membership is a provenance-bearing snapshot and may require explicit refresh.
- Exports are paginated and bounded but not transactionally consistent across concurrent membership changes. A host must control export destination, retention, privacy and access policy.
- Performance gates measure synthetic datasets and shared CI runners; p50/p95 guardrails are **not production SLAs**, and there is no proven durable outbox/exactly-once transport.

## Candidate installation (only after retrieving a verified CI artifact)

The GitHub Actions workflow named **Campaign RC1 Distribution Qualification** produces an isolated wheel/sdist archive on the candidate branch. Download and verify the SHA-256 manifest from the **same exact Git commit**. Then, for example, install a locally retrieved wheel:

```bash
python -m pip install --no-deps ./pycrmkit-1.2.0rc1-py3-none-any.whl
python -c "import pycrmkit; print(pycrmkit.__version__)"
```

For the FastAPI/PostgreSQL reference, install the documented extras and apply **packaged** migrations before starting the host. Do **not** use `pip install pycrmkit==1.2.0rc1` as evidence of PyPI availability until the release is actually published there.
