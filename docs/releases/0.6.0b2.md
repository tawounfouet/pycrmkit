# PyCRMKit 0.6.0b2 — PostgreSQL

`0.6.0b2` qualifies PostgreSQL as the production-reference persistence backend
for the SQLAlchemy adapter introduced across `0.6.0a1`–`0.6.0b1`.

## Added

- optional `postgresql` installation extra with psycopg 3;
- dedicated GitHub Actions workflow backed by a live PostgreSQL 17 service;
- live schema/constraint/index introspection;
- PostgreSQL foreign-key error qualification;
- Unicode, timezone-aware datetime, Decimal, JSON and Custom Field round trips;
- concurrent write qualification using independent SQLAlchemy Sessions;
- commit-time SQLAlchemy/PostgreSQL error translation into PyCRMKit errors.

Install the production-reference adapter dependencies with:

```bash
pip install "pycrmkit[postgresql]"
```

## Database-enforced invariants

The PostgreSQL qualification exposed invariants that cannot safely rely on an
application-side pre-check under concurrency.

Tag persistence now stores the normalized domain key explicitly and enforces a
named uniqueness constraint:

```text
TagName("VIP")  ─┐
                 ├─ normalized_name = "vip" ─→ UNIQUE
TagName("vip")  ─┘
```

Tag assignments also enforce the tuple
`(tag_id, entity_kind, entity_id)` as a database uniqueness constraint.

These constraints preserve repository semantics even when two independent
transactions race after both passing their application-level existence checks.

## Backend-neutral failures

SQLAlchemy/driver exceptions are not exposed as the public persistence contract.

At commit time PostgreSQL SQLSTATE values are translated into PyCRMKit errors,
including:

- `23505` → `DuplicateError` / `repository.duplicate`;
- `23503` → `RepositoryError` / `repository.foreign_key_violation`;
- `23502` → `repository.not_null_violation`;
- `23514` → `repository.check_violation`;
- `40001` → `repository.serialization_failure`;
- `40P01` → `repository.deadlock`.

Only safe diagnostic metadata such as SQLSTATE and constraint/table/column names
is exposed. SQL statements and parameter values are not copied into the
PyCRMKit error context.

## Concurrency qualification

The release includes a deterministic two-session race against the normalized
Tag uniqueness invariant.

Both transactions reach the write boundary before either commits. PostgreSQL
accepts one transaction and rejects the competing commit; the Unit of Work
converts the backend violation into `DuplicateError`.

## Schema lifecycle

`Base.metadata.create_all(...)` remains useful for tests and local
experimentation in this beta.

It is **not** the production schema-evolution mechanism. Versioned migrations,
empty-database upgrade paths and previous-version upgrade qualification arrive
in **`0.6.0b3 — Alembic / Migrations`**.
