# PyCRMKit 0.4.0 — Communication Stable

`0.4.0` promotes the fully qualified `0.4.0rc1` Communication line to
stable without adding new business scope.

## Stable scope

- provider-neutral Communication domain;
- typed communication intents, delivery attempts and CRM records;
- provider-neutral `EmailProvider` protocol;
- direct and templated email composition;
- optional Jinja2 rendering;
- standard-library SMTP provider;
- optional Resend provider;
- transactional `crm.email` facade;
- normalized delivery/open/click/bounce/failure lifecycle events;
- append-only Communication delivery history;
- idempotent provider callback replay;
- out-of-order callback protection;
- Communication Timeline projection;
- Memory Communication persistence;
- stable `0.4.x` public API contract.

## Stable guarantees

The final qualification preserves the release-candidate guarantees:

1. provider transport acceptance is distinct from downstream mailbox delivery;
2. email send state and CRM history commit transactionally in Memory;
3. idempotency keys prevent duplicate committed outbound sends;
4. provider callbacks resolve through provider message identity;
5. external callback IDs make provider replay idempotent when supplied;
6. out-of-order callbacks remain in history without regressing current state;
7. all seven normalized `email.*` lifecycle names are supported;
8. recipient addresses and message bodies are excluded from emitted event payloads;
9. Communication projects directly into Timeline rather than duplicating Activity;
10. SMTP and Resend both satisfy the provider-neutral contract;
11. stable `0.1`–`0.3` facade contracts remain compatible.

## Stable facade surface

```text
crm.email.send
crm.email.record_delivery_event
crm.email.get
crm.email.for_contact
crm.email.for_organization
crm.email.delivery_history
```

The complete contract is documented in `docs/api/0.4-public-api.md`.

## Runtime qualification

The stable release is qualified on Python 3.11, 3.12 and 3.13 through GitHub
Actions, together with communication domain/provider/template/SMTP/Resend
tests, delivery-event mapping, Memory integration, Communication history E2E,
stable `0.1`–`0.3` regression, Ruff, mypy strict, MkDocs strict, package
build, wheel installation and installed-package functional smoke.

Ordinary CI uses deterministic fakes and does not contact live SMTP or Resend
services.

## Architecture decision: Timeline, not mirrored Activity

Stable `0.4.0` realizes CRM relationship history through direct
Communication → Timeline projection. It does not create duplicate email
Activity rows. `CommunicationRecord` remains authoritative for provider and
delivery semantics while Timeline is the cross-domain customer-history model.

## Deferred scope

Durable event/webhook infrastructure begins in `0.5.x`. Production
SQLAlchemy/PostgreSQL persistence remains scheduled for `0.6.x`.

The next implementation milestone is **`0.5.0a1 — Event Registry & Serialization`**.
