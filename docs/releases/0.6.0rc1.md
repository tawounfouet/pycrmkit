# PyCRMKit 0.6.0rc1 — Persistence Qualification

`0.6.0rc1` qualifies the complete `0.6.x` persistence line as one coherent
release candidate before promotion to `0.6.0` stable.

The release candidate does not introduce a new CRM bounded context. It validates
that the stable `0.1`–`0.5` domain/facade surface behaves correctly when
backed by SQLAlchemy, PostgreSQL, transactional Unit of Work semantics and
versioned Alembic migrations.

## Qualified persistence path

```text
Stable CRM facade 0.1–0.5
          ↓
Repository contracts
          ↓
SQLAlchemy repositories
          ↓
SQLAlchemy Unit of Work
          ↓
PostgreSQL 17
          ↓
Alembic revision 0002
```

The release-candidate gate exercises this path end-to-end on a database created
by `alembic upgrade head`.

## Stable 0.1–0.5 scenario on PostgreSQL

The RC qualification traverses the stable public surface in one durable CRM
scenario:

- Contacts, Organizations, Relationships, Tags and Custom Fields;
- Activities, Tasks and Timeline;
- Leads, Opportunities and Pipeline transitions;
- Communication send/delivery history;
- Eventing, webhook registration, retry and delivery history.

The scenario then constructs a fresh CRM runtime using new SQLAlchemy Sessions
and verifies that the resulting state can be reloaded from PostgreSQL.

## Repository conformance on PostgreSQL

The reusable SQLAlchemy repository contract suite now runs against both:

- SQLite for lightweight adapter qualification;
- PostgreSQL for production-reference conformance.

The PostgreSQL execution exposed a contract mismatch that SQLite had not made
visible: several database-level foreign keys imposed cross-aggregate existence
requirements that the repository protocols themselves do not require.

The RC therefore aligns persistence with the domain contracts.

### Cross-aggregate references

The following fields remain typed/reference IDs and indexed for querying, but
are no longer protected by database foreign-key constraints:

- `Lead.contact_id`;
- `Lead.organization_id`;
- `Opportunity.contact_id`;
- `Opportunity.organization_id`;
- `WebhookDelivery.subscription_id`.

This preserves adapter equivalence: a repository can persist its aggregate
without silently introducing a stronger precondition than the repository
protocol specifies.

### Ownership foreign keys remain enforced

Foreign keys that model persistence ownership remain intact. Examples include:

- Tag Assignment → Tag;
- Communication child rows → Communication Intent/Record;
- Delivery Attempt → Communication Intent;
- Webhook Delivery Attempt → Webhook Delivery;
- normalized child tables for Contacts, Organizations and Pipelines.

PostgreSQL FK violations on these relationships continue to be normalized into
backend-neutral PyCRMKit errors.

## Alembic revision 0002

The release candidate advances the migration head to:

```text
0001  persistence baseline
  ↓
0002  align repository reference semantics
```

Revision `0002` removes only the five non-contractual cross-aggregate foreign
keys described above.

It does not drop the reference columns, indexes or CRM data.

The migration suite verifies:

- empty database → `upgrade head`;
- `0001 → 0002` upgrade with persisted data preserved;
- head → base → head lifecycle;
- SQLAlchemy metadata parity at head;
- no migration drift;
- the intended cross-aggregate FKs exist at `0001` and are absent at
  `0002`.

## Transaction qualification

The RC includes explicit PostgreSQL rollback qualification across multiple
repositories participating in one Unit of Work.

A failure before commit must leave no partial Contact or Organization state.

The existing transaction guarantees remain:

- repositories never commit independently;
- all repositories in one UoW share one Session;
- context exit without commit rolls back;
- database commit occurs before post-commit event publication;
- commit-time backend exceptions are translated to PyCRMKit persistence errors.

## Installed-wheel qualification

The persistence gate builds the real wheel and creates a fresh virtual
environment.

The clean environment then:

1. installs the wheel with migration/PostgreSQL dependencies;
2. invokes the packaged `pycrmkit-migrate` command;
3. upgrades an empty PostgreSQL database to the packaged migration head;
4. runs `current` and `check`;
5. executes a CRM + Sales persistence smoke test against PostgreSQL.

The smoke environment does not depend on the editable `src/` tree.

This verifies that the migration assets required by an installed consumer are
actually present in the wheel.

## Quality gates

The release candidate must pass together:

- stable `0.1`–`0.5` PostgreSQL scenario;
- PostgreSQL repository conformance;
- transaction rollback qualification;
- migration lifecycle and drift checks;
- installed-wheel + packaged-migrations + PostgreSQL smoke;
- PostgreSQL 17 qualification;
- Python 3.11, 3.12 and 3.13;
- Ruff;
- strict mypy;
- documentation build;
- package build;
- aggregate CI.

## Compatibility

The stable `0.1`–`0.5` public CRM facade remains unchanged.

`0.6.0rc1` freezes the persistence behavior for final qualification. Changes
between this release candidate and `0.6.0` stable should be limited to
release-blocking defects, documentation corrections and packaging/release
engineering.
