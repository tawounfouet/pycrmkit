## Purpose and change scope

Stable `1.2.0` will promote the feature-frozen [Campaign 1.2 RC contract](1.2.0rc1.md) without introducing any new marketing, delivery or identity-management feature. Relative to stable 1.1, the *planned* publicly supported additions are:

- Campaign metadata, lifecycle, optimistic `expected_revision` and PATCH omitted/null/value behavior.
- Direct membership, captured static Segment sources, deduplicated audience and provenance.
- Attribution references and CommunicationRecord **link metadata**; no message body or delivery capability in these links.
- Opt-in FastAPI and DRF Campaign routes with **host-verified** identity/action/resource/scope authorization; generic CRM endpoints are not automatically tenant-safe.
- Bounded CSV/JSON/JSONL direct-member imports (up to 1,000 rows) and paginated direct/audience/source exports with explicitly documented recovery and privacy boundaries.
- Equivalent domain contracts across Memory, SQLAlchemy/PostgreSQL, and the native Django ORM adapter.

See the [Campaign guide](../campaigns/index.md), [Campaign DataOps guide](../data_operations/campaigns.md), [host security guide](../integrations/1.2.0b3-campaign-security.md) and [stable compatibility/support contract](../reference/1.2.0-support-and-compatibility.md).

## Upgrade from 1.1.0 or 1.2.0rc1

Follow the [1.2 upgrade guide](../getting-started/1.2.0-upgrade.md) before enabling Campaign operations. Campaign persists only through application-selected, explicitly migrated adapters. Alembic head remains **`0006_campaign_persistence`**; native Django migrations remain **`0005_communication_record_store`**. These are distinct migration authorities and **must not** concurrently manage incompatible Campaign physical tables in the same database schema.

No automatic conversion of existing host records, new schema revision just for the stable label, or forced migration between SQLAlchemy and Django is implied. The consuming host must qualify backups, restore, ownership, permissions, and rollback.

## DataOps and security limits

- Import operations commit accepted direct-member rows individually; an interrupted batch may leave a committed prefix. Retry the complete authorized input with [documented replay reconciliation](../data_operations/campaign-recovery.md); direct-member deduplication is **not** distributed exactly-once.
- Offset-paged exports are not snapshot-consistent while the membership set changes. The consumer must use a controlled stationary dataset or host snapshot/reconciliation when required.
- Generic CSV may trigger spreadsheet formulas; use the [documented consumer guard](../data_operations/1.2.0rc1-campaign-export-consistency-privacy.md) and a separately labelled safe-spreadsheet derivative when appropriate.
- Contact IDs, source information and Campaign provenance may be personally identifiable. Host-owned IAM, tenant constraints, purpose limitation, encryption, retention/deletion and logging controls remain mandatory.
- Synthetic signed-HMAC reference-host tests are **not** enterprise IAM, OAuth/OIDC, GDPR or SOC 2 certification; never deploy the CI-only `trust` database authentication configuration.
