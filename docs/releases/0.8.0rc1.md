# PyCRMKit 0.8.0rc1 — Django Example + E2E

`0.8.0rc1` qualifies the complete current Django integration path against a
real PostgreSQL 17 database and from the built wheel.

## Delivered

```text
examples/django/
├── manage.py
├── compose.yaml
├── .env.example
├── README.md
```

```text
Django 5.2
  ↓
Django admin + DRF
  ↓
PyCRMKit CRM facade
  ↓
DjangoTransactionBridge
  ↓
Django repositories
  ↓
PostgreSQL 17
```

## Deployment flow

```text
install wheel + django/drf/postgresql extras
    ↓
configure PYCRMKIT_DATABASE_URL
    ↓
python manage.py migrate
    ↓
python manage.py check
    ↓
start Django
```

Migrations remain explicit and adapter-specific. Application import/startup does
not mutate the database schema.

## E2E journey

The source-checkout gate:

```text
fresh PostgreSQL schema
    ↓
Django migrations
    ↓
POST Contact
    ↓
POST Organization
    ↓
POST Relationship
    ↓
persist IDs
    ↓
fresh Python/Django process
    ↓
GET all three resources
    ↓
PATCH Contact
    ↓
POST Relationship/end
    ↓
admin smoke
    ↓
migration-record verification
```

The PostgreSQL schema is then dropped and recreated, the built wheel is installed
into a clean virtual environment with `[django,drf,postgresql]`, and the same
migration/E2E journey is repeated.

## Architecture boundary

This RC intentionally does not broaden the Django persistence adapter.

Durable Django-backed CRM scope remains:

```text
Contacts
Organizations
Relationships
```

`DjangoTransactionBridge` therefore remains a bounded integration bridge, not
the complete cross-domain PyCRMKit `UnitOfWork`.

The reference CRM wiring disables audit persistence because no Django audit
repository exists yet. Domain events remain enabled and are published only after
successful transaction commit.
