# PyCRMKit 1.1.0b1 — SQLAlchemy/PostgreSQL Segmentation

This release implements **PV1-LOT-004**.

## Delivered

~~~text
Portable QueryExpression
        ↓
SQLAlchemySegmentQueryExecutor
        ↓
database-side predicates
        ↓
Contact / Organization / Lead / Opportunity
        ↓
PostgreSQL / SQLAlchemy
~~~

The beta also persists:

~~~text
Segment
SegmentMember
SavedQuery revision history
~~~

through migration **0005**.

## SQLAlchemy persistence

New tables:

~~~text
pycrmkit_segments
pycrmkit_segment_members
pycrmkit_saved_queries
~~~

`Segment` remains current-state persistence.

`SavedQuery` remains append-only revision history:

~~~text
(saved_query_id, revision)
~~~

Static memberships are stored independently from target CRM entities and preserve
the existing typed `EntityReference` boundary.

## Query compiler

The SQLAlchemy query executor implements the same portable expression model used
by Memory:

~~~text
eq / ne
lt / lte / gt / gte
in / not_in
is_null / is_not_null
contains
starts_with
ends_with
and / or / not
~~~

It supports:

- core fields for Contact, Organization, Lead and Opportunity;
- Tag membership through database `EXISTS` predicates;
- supported scalar Custom Fields;
- relative time resolved from the injected `Clock`;
- explicit deterministic ordering;
- stable entity-ID tie breaking;
- exact count + offset pagination.

The compiler keeps SQLAlchemy objects inside the adapter. Domain services and
the public facade continue to use only provider-neutral `QueryExpression`
objects.

## Semantic parity

Portable null behavior remains two-valued:

~~~text
non-null predicate against missing value = false
NOT(false)                              = true
~~~

This is enforced explicitly rather than inheriting SQL three-valued NULL
behavior.

Tag and Custom Field filters preserve the Memory reference semantics, including
absence-aware null checks.

## Unit of Work

`SQLAlchemyUnitOfWork` now exposes the optional capabilities:

~~~text
segments
segment_memberships
segment_query_executor
saved_queries
~~~

Therefore the existing facade works without a SQLAlchemy-specific public API:

~~~python
crm.segments.create_dynamic(...)
crm.segments.evaluate(...)
crm.saved_queries.create(...)
crm.saved_queries.execute(...)
~~~

## Migration

Alembic head advances:

~~~text
0004_task_type
      ↓
0005_segmentation_persistence
~~~

The migration is additive. Existing 1.1.0a3 Task rows and all V1 CRM tables are
preserved.

## Qualification

The SQLAlchemy adapter tests run both on SQLite for fast semantic feedback and on
the supported PostgreSQL compatibility matrix.

The release line continues to qualify PostgreSQL 16/17 with SQLAlchemy 2.0/2.1.
