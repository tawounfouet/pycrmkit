# PyCRMKit 1.2.0b1 — SQLAlchemy/PostgreSQL Campaign Persistence

This release implements **PV1-LOT-011**.

## Delivered

PyCRMKit now persists the complete Campaign contract introduced across
`1.2.0a1` through `1.2.0a3` with the SQLAlchemy/PostgreSQL adapter.

~~~text
Campaign
├── metadata / lifecycle / optimistic revision
├── direct audience members
├── attached Segment sources
│   └── captured Segment members
├── attribution references
└── communication links
~~~

The public `crm.campaigns` facade remains unchanged. Applications switch
storage adapters without receiving ORM models or SQLAlchemy expressions.

## SQLAlchemy persistence

The beta adds six Campaign-owned tables:

~~~text
pycrmkit_campaigns
pycrmkit_campaign_members
pycrmkit_campaign_segment_sources
pycrmkit_campaign_segment_members
pycrmkit_campaign_attributions
pycrmkit_campaign_communication_links
~~~

Ownership foreign keys cascade only inside the Campaign aggregate boundary.

There are deliberately no database foreign keys from Campaign persistence to
Segment, CommunicationRecord, Contact, Organization, Lead or Opportunity.
Those remain cross-aggregate references and preserve the same semantics as the
Memory adapter.

## Unit of Work

`SQLAlchemyUnitOfWork` now exposes:

~~~text
campaigns
campaign_audience
campaign_linkage
~~~

All three repositories share the same SQLAlchemy `Session` as the rest of the
CRM repositories.

Therefore multi-table Campaign operations remain atomic:

~~~text
Campaign mutation
+ audience / linkage persistence
+ Audit
+ staged DomainEvent
        ↓
single database commit
        ↓
post-commit event publication
~~~

A rollback clears all uncommitted Campaign rows and staged events.

## Optimistic concurrency

Campaign updates use an atomic SQL compare-and-swap:

~~~sql
UPDATE pycrmkit_campaigns
SET ...
WHERE id = :campaign_id
  AND revision = :previous_revision
~~~

A stale writer cannot silently overwrite a committed revision. Competing
PostgreSQL transactions are qualified to converge to one successful update and
one `campaign.revision.conflict`.

## Audience persistence

Direct members and captured Segment members retain provenance independently.

The final Campaign audience is computed from:

~~~text
direct members
UNION
captured Segment members
~~~

The SQL `UNION` is the canonical de-duplication boundary. Pagination and
`audience_count()` derive from the same relation.

Attaching or refreshing a Segment source validates the complete capture before
mutation. The source row is persisted before its captured members inside the
same transaction so PostgreSQL ownership constraints remain valid without
weakening rollback atomicity.

## Attribution uniqueness

The Memory contract treats an absent external reference as part of the logical
attribution key.

SQL persistence therefore normalizes:

~~~text
Domain None
    ↕
Database ""
~~~

This preserves duplicate protection on PostgreSQL where ordinary nullable
unique columns would otherwise allow multiple `NULL` values.

## Migration 0006

Alembic head advances:

~~~text
0005_segmentation_persistence
          ↓
0006_campaign_persistence
~~~

Revision `0006` is additive:

- no existing V1 or 1.1 table is altered;
- existing rows are untouched;
- the six Campaign tables are created in dependency order;
- downgrade removes only the six Campaign tables;
- the migration exists in both the development and packaged migration trees.

Qualification covers:

~~~text
empty database → head
0005 → 0006
0006 → 0005
0005 → 0006 again
Base.metadata drift == []
stable 1.1 fixture preserved
packaged migration == development migration
~~~

## Repository and PostgreSQL qualification

The beta includes mirrored Memory/SQLAlchemy repository contracts for Campaign,
Audience and Linkage semantics.

Live PostgreSQL qualification covers:

- Campaign revision races;
- concurrent duplicate direct members;
- concurrent duplicate attributions including `external_ref=None`;
- ownership constraints;
- atomic Segment capture rollback;
- no event publication on rollback;
- timezone-aware timestamp round trips;
- nested JSON metadata round trips.

## Historical 1.1 evidence

PyCRMKit 1.1 remains the stable compatibility baseline.

The frozen `1.1.0rc1` and `1.1.0` checksums and migration-head evidence are
not modified by this release. Their reproducibility workflow pins the original
qualified build toolchain so later setuptools/Python patch releases cannot
create false artifact drift.
