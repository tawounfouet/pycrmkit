# Preparing for PyCRMKit 1.2.0 (Upgrade Guide)

**Status: PREPARED / NOT PUBLISHED.** The `1.2.0` package has **not** been promoted or published. Current stable is `1.1.0`; GitHub Campaign RC is `1.2.0rc1`. **Do not** run an unverified `pip install pycrmkit==1.2.0`.

## Before adopting the Campaign 1.2 line

1. Inventory installed package version, Python version and adapters; consult [supported matrix](../reference/1.2.0-support-and-compatibility.md). Record your current application schema and migration owners.
2. Back up application data and test restore in a disposable environment. Review contact/Segment ownership and host tenant policy before enabling any Campaign route.
3. Move to the approved source distribution only when one exists. At present, [GitHub `v1.2.0rc1`](https://github.com/tawounfouet/pycrmkit/releases/tag/v1.2.0rc1) is the published Campaign prerelease. Its GitHub publication alone does **not** establish a PyPI index version.
4. In a throwaway environment, install the verified wheel with the **specific** extras used by your host (e.g. `[fastapi,postgresql,migrations]`, `[django]`, `[drf]`). The core remains headless. The stable wheel's exact filename and digest cannot be known until LOT-32-010/012.
5. Apply **only the selected adapter's migration history**: Alembic `pycrmkit-migrate upgrade head` and `current`/`check` for SQLAlchemy/PostgreSQL; or Django `python manage.py migrate` and `makemigrations pycrmkit_crm --check --dry-run` for the native Django adapter. Do **not** combine both incompatible migration owners against one Campaign schema.
6. Verify `crm.campaigns` create/get/update with `expected_revision`, direct and captured Segment audiences, attribution metadata, Communication links and the optional FastAPI/DRF handlers behind a trusted, explicit `CampaignSecurityBoundary`. Verify 401/403 for foreign tenants **before** release cutover.
7. For DataOps: capture source hashes and run IDs, validate at most 1,000 rows, pre-authorize and pre-scan owned entities, replay interrupted input only after inspecting committed direct membership. Export to a protected staged file; reconcile stationary snapshot expectations, then publish atomically. Guard spreadsheet derivatives.
8. Run a full restart/recovery test: reopen a new CRM/UoW instance against the migrated backend and confirm owned Campaign records, audience counts and metadata references persist.

## Compatibility with existing consumers

The 1.0/1.1 CRM and Segmentation contracts remain frozen; Campaign 1.2 is additive to the earlier stable feature line. The *stable promotion* should introduce **no functional change** relative to `1.2.0rc1`. If a public interface, error envelope, event payload or persistence behavior changes, stop and qualify an explicit release candidate or corrective plan instead of silently deploying.

## Rollback

- If upgrade validation fails **before production cutover**, leave the existing installed version and database unchanged; restore the disposable environment and file an issue with sanitized logs and the exact package SHA.
- If already deployed, block incoming writes, preserve audit and backup evidence, and follow an application-owned, **verified rollback** plan. Do **not** assume downgrading a wheel reverses database migrations or data written under a newer schema.
- If data/schema compatibility is uncertain, take a backup and stop; do not force `downgrade` or manually edit `alembic_version` / `django_migrations` to manufacture success.
- Release publication failures use the separate [stable publication runbook](../development/1.2.0-stable-release-gate.md). For import recovery see [Campaign replay playbook](../data_operations/campaign-recovery.md).

## After verified stable publication

Only LOT-32-013 may update these instructions to point to the final verified `v1.2.0` wheel, tag, source SHA, SHA-256 and actual PyPI status. Until then this is a **preparation guide** and not a deployment claim.
