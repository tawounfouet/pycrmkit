# PyCRMKit 1.2.0 - Proposed Support & Compatibility Contract

**Status: PREPARED / NOT PUBLISHED.** This is the intended support boundary for the future `1.2.0` stable line, not proof of its publication. The **currently published stable** is `1.1.0`; the GitHub Campaign prerelease is `1.2.0rc1`.

## Declared package constraints and qualification scope

| Component | Declared / qualified family | Scope |
|---|---|---|
| Python | `>=3.11,<3.14` | Explicit test matrix: **3.11, 3.12, 3.13** |
| SQLAlchemy (opt-in) | `>=2.0,<2.2` | 2.0.x and 2.1.x; PostgreSQL-backed qualification |
| PostgreSQL | **16 and 17** | Reference database matrix, not a promise about other versions |
| psycopg binary (postgresql extra) | `>=3.2,<3.4` | Driver adapter dependency |
| FastAPI (opt-in) | `>=0.141,<0.142` | 0.141.x with Pydantic 2.13.x |
| Pydantic (fastapi extra) | `>=2.13,<2.14` | Request/response DTO boundary |
| Django (opt-in) | `>=5.2,<5.3` | 5.2.x native ORM adapter |
| Django REST Framework (opt-in) | `>=3.18,<3.19` | 3.18.x optional HTTP transport |
| Memory | Standard Python runtime | Domain contract reference; **not** durable storage |
| Core-only install | `pip install pycrmkit` (when obtained from a verified source) | Does not require SQLAlchemy, Django, DRF, FastAPI or provider SDKs |

The table is derived from `pyproject.toml` constraints and existing CI qualification, **not** a promise that every Cartesian product of all Python/framework/database minor versions has been tested. Stable `1.2.0` installed archives require separate qualification in LOT-32-010. Providers, OS, database hosting and extras outside the declared ranges are not supported without a new explicit gate.

## Frozen API and migration compatibility

- Public CRM V1/V1.1 and Campaign V1.2 facade, DTO, event envelopes and 401/403/409/422 transport semantics are subject to frozen contract tests. Stable promotion should not add a Campaign field, type, status or required behavior compared with the published `1.2.0rc1`.
- Existing PostgreSQL SQLAlchemy/Alembic **`0006_campaign_persistence`** and native Django **`0005_communication_record_store`** remain separate migration heads. The `1.2.0` package label **does not** create a new schema migration.
- **No automatic cross-adapter database swap.** Physical Django and SQLAlchemy Campaign schemas/migration ownership differ. Explicitly choose one migration authority for the Campaign tables.
- Normalised Campaign keys, event code semantics, optimistic locking, Segment snapshot capture and direct-member audience union retain their 1.2 RC contract.

## Host versus library security

PyCRMKit is a **headless library**. The application host must authenticate principals and authorize tenant, Campaign, referenced entity and operations **before** invoking Campaign HTTP, Python facade, imports, exports, jobs and file downloads. No global IAM/OIDC, row-level tenant isolation, default authorization of generic CRM routes, retention service, or GDPR/SOC2 attestation is provided. The signed HMAC reference host demonstrates a *test-only fixture*; it is not production identity infrastructure.

DataOps replay deduplicates direct members but **is not an atomic bulk import**. Offset export under concurrent writes **is not snapshot consistent**. Canonical CSV **is not automatically spreadsheet safe**; text-column import or an explicitly validated, separately labelled derivative is required. Identifiers and provenance can still be private data.

## Versioning, fixes and deprecation

- The planned `1.2.0` release is a **minor, compatibility-preserving promotion**, not a reason to ship new features. If approved, incompatible changes need separate versioning, review and documented migration.
- Corrections with no incompatible contract change may be proposed as **`1.2.1`**; all maintenance releases need their own tests, exact source SHA, release decision, checksum and publication.
- Deprecations require explicit notice, migration alternative, compatibility testing and a documented decision before removal. **No fixed depreciation window or deadline is approved.**
- **No promised support duration, end-of-life date, response-time SLA, security patch frequency or guaranteed hosted uptime** appears in the current release contract. Those need explicit maintainer authorization and publication of a policy amendment.
