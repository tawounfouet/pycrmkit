# PyCRMKit 1.2.0 - LOT-32-003 Host Security & Privacy Acceptance

Date: 2026-10-30. Branch: release/1.2.0-campaign-metadata-stable. PR: #113 (draft). Reference: published v1.2.0rc1 source 5113cedb50750185e457505dfcca5519ce3a62bd. Version remains 1.2.0rc1.

## Security boundary and scope

This is a risk-based acceptance of the *library's* existing opt-in Campaign security boundary and the disposable signed host example; it is **not** a certification of enterprise IAM, production JWT/OIDC, tenant row-level security, GDPR compliance, or safe operation of legacy non-Campaign routes.

PyCRMKit offers CampaignPrincipal, CampaignSecurityBoundary, and explicit FastAPI/DRF Campaign adapters. The host must prove credentials, authorize action + resource + scope, bind tenant ownership before accessing a CRM factory, separately protect DataOps Python/CLI/jobs, and govern logs, encryption, retention, consent, erasure and audit. Arbitrary X-Actor-ID, X-Correlation-ID and client-supplied owner_id are not trust anchors.

The reference host uses signed *test-only* HMAC bearer claims (issuer, audience, subject, tenant, role, iat, exp); the test key is disposable, not a production identity provider. PostgreSQL 17 in GitHub Actions uses an isolated trust-auth fixture. No claim about real deployment secrets, revocation or security configuration follows from it. Its Communication record metadata tenant marker is synthetic and not an authoritative IAM source.

The stable workflow campaign-stable-compatibility.yml includes a dedicated IAM-fixture/tenant/privacy test step, plus the existing HTTP compatibility gate. The existing Campaign RC1 installed-wheel production-host workflow continues to exercise PostgreSQL 17 and wheel-installed Alembic, host token verification, tenant-constrained capture/import/export/linkage, denied references and restart. Exact-SHA CI results must be attached to PR #113; the source file deliberately does not claim unobserved success.

No migrations, public API, domain source, integrations or package version are changed in LOT-32-003, preserving LOT-32-002's source-vs-RC invariants. Test additions assert negative outcomes and sensitive-data field allowlists. Any blocker fix later requires review and fresh candidate qualification.

## Explicit unresolved deployment prerequisites

1. Real IAM/JWT/OIDC/session signature, issuer/audience, expiration, replay/revocation, key rotation, role/tenant mapping and monitoring in the consumer host.
2. Verified tenant authorization across **all** HTTP routes, data operations, scheduled jobs and direct Python invocations; never adopt an allow-all authorizer or assume owner_id is system-wide tenancy.
3. Production secrets, least-privilege DB credentials, TLS, actual RLS/DB tenant-scoping strategy, backup and audit validation. CI trust PostgreSQL authentication is not production guidance.
4. Data minimization and lawful basis, PII classification of UUID/provenance/segment identifiers, encrypted exports, TTL/deletion, DSAR workflows, logging redaction and incident response.
5. Generic CSV is not a safe human spreadsheet file. Use the host consumer guard and text-column import, or transform a separately labelled derivative.
6. Offset exports remain best effort during mutation. A consistent snapshot must be provided by the host if necessary.
