## Qualification boundary: the version sequence matters

The frozen RC implementation plan deliberately postpones the **actual source-of-truth version change** from `1.2.0b3` to `1.2.0rc1` until **LOT-31-015 - RC Version & Release Documentation**. Consequently, this LOT tests *candidate-branch code* installed from wheel and sdist with package metadata `1.2.0b3`. It does **not** claim to have installed, hashed or published files named `pycrmkit-1.2.0rc1*`. That final RC-metadata gate MUST be rerun after LOT-31-015 on the actual candidate commit and remains a hard GO/NO-GO requirement under LOT-31-016.

The existing V1 Public API freeze manifest `tests/compatibility/public_api_v1_candidate.json`, V1.1 manifest and Campaign 1.2 manifest are **immutable** in this lot. The Campaign 1.2 manifest intentionally lists b3 as baseline and rc1 as target; it must not be rewritten merely to make a test pass.

## 1. Executable compatibility and distribution matrix

The existing `.github/workflows/compatibility-matrix.yml` qualifies:
- Python 3.11, 3.12, 3.13 (source checkout and public API smoke);
- PostgreSQL 16/17 × SQLAlchemy 2.0/2.1 × psycopg 3.2/3.3: eight live combinations;
- FastAPI 0.141 / Pydantic 2.13 on Python 3.11 and 3.13;
- Django 5.2 / DRF 3.18 on Python 3.11 and 3.13;
- core-only; individual optional extras `sqlalchemy`, `postgresql`, `migrations`, `fastapi`, `django`, `drf`, `email`, `resend`; combined FastAPI/PostgreSQL/migrations and Django/DRF/PostgreSQL.

**LOT-31-013 closes the source-versus-distribution gap** via the new `.github/workflows/campaign-rc1-distribution-qualification.yml`. For **each** of Python 3.11, 3.12, 3.13, it:
1. builds both wheel and sdist from that exact checkout and passes `twine check`;
2. verifies exact distribution filenames/version, `Requires-Python`, the full set of advertised extras, public Python package resources, Django 0001–0005 migration files and Alembic 0001–0006;
3. computes independent SHA-256 hashes of both built distributions and saves the artifact manifest;
4. installs **wheel core-only** into its own temporary venv, executes existing V1 installed-artifact smoke **outside the checkout** with `PYTHONPATH=""` and isolated interpreter `-I`, runs the Campaign DataOps smoke and `pip check`;
5. repeats the same qualification from **sdist core-only** in another clean venv;
6. on Python 3.13 additionally installs **wheel and sdist with all advertised runtime extras** in two fresh venvs, runs V1 + Campaign DataOps smokes, invokes packaged `pycrmkit-migrate --help` and `pip check`.

`-I` and execution from `/tmp` mean the smoke cannot accidentally import `pycrmkit` from the repository. The existing smoke explicitly checks installed `importlib.metadata`, migration resources, version and the optional-dependency boundary; core-only installs must not see Django, DRF, FastAPI, SQLAlchemy, Alembic, psycopg, Jinja2 or Resend. Full-extra installation validates their presence. Installing a full-feature extras bundle does **not** mean Django's narrow CommunicationRecordStore is an implemented full delivery backend.

## 2. Packaged-migration contract

**Alembic resources** are shipped in the `pycrmkit` wheel and in sdist:

- `storage/sqlalchemy/migrations/env.py`, `cli.py`, `README.md`, `script.py.mako`;
- `0001_persistence_baseline`, `0002_align_repository_reference_semantics`, `0003_external_identities`, `0004_task_type`, `0005_segmentation_persistence`, `0006_campaign_persistence`.

**Django ORM migration resources:** `0001_initial`, `0002_external_identity`, `0003_segmentation`, `0004_campaign_persistence`, `0005_communication_record_store`.

`pycrmkit-migrate --help` checks console script installation. The **actual database-side migrate/rollback/upgrade** is independently tested from a packaged wheel with real PostgreSQL in the existing `Migrations`, `Production Persistence & Migrations`, `Django PostgreSQL E2E` and `FastAPI PostgreSQL E2E` workflows. A `--help` invocation alone must never be claimed as migration qualification. Django and Alembic must manage separate physical schemas; the 1.2 Campaign schema layouts are not interchangeable.

## 3. Integrity / SHA256 evidence

`scripts/rc1_distribution_manifest.py` generates `rc1-distribution-manifest-py3.13.json` (and local equivalents for 3.11/3.12) containing **actual** wheel/sdist filenames, byte sizes, SHA-256 digests, supported Python/extras and the packaged migration lists. The Python 3.13 job uploads that manifest **alongside the archives** as the `campaign-rc1-distribution-qualification` GitHub Actions artifact.

Those SHA values refer to CI-built **pre-RC b3-labeled artifacts**, not permanent release checksums. Canonical reproducible RC SHA-256 generation and verification against the final tagged commit belong to LOT-31-016. Never publish a hash calculated against the b3 baseline as a `1.2.0rc1` checksum.

Negative unit tests `tests/compatibility/test_rc1_distribution_manifest.py` deliberately assert that changed metadata version, changed supported Python interval, missing extra or missing required migrations cause qualification to fail. The manifest inspector raises an error on missing wheel/sdist files, unexpected archive members, missing embedded migrations or entry point. The wheel must not bundle test, example, scripts or CI directories.

## 4. Reproduction and security

```bash
python -m pip install --upgrade "build>=1.2" "twine>=6" "pytest>=8"
pytest tests/compatibility/test_rc1_distribution_manifest.py -q
python -m build
python -m twine check dist/*
python scripts/rc1_distribution_manifest.py \
  --dist dist --expected-version 1.2.0b3 \
  --output rc1-distribution-manifest.json
```

All installation checks must run from **fresh disposable venvs** and an external working directory with `PYTHONPATH` cleared, as in the versioned CI workflow. Never test against a production database or install the candidate to public PyPI during qualification.
