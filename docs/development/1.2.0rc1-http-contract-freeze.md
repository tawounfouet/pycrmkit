## 1. Why a separate HTTP freeze?

The Campaign facade and V1/V1.1 compatibility manifests are covered in LOT-31-002. HTTP transports require *additional* evidence: an unchanged Python function signature does not prove that FastAPI OpenAPI or DRF's rendered JSON and response status are unchanged.

This lot freezes **actual transport observations**, while preserving the architecture:

```text
Host identity and authorization
        |
        v
FastAPI router / DRF ViewSet
        |
        v
crm.campaigns facade
        |
        v
Domain / repository / Memory-SQLAlchemy-Django adapter
```

Neither the FastAPI nor the DRF adapter implements a separate Campaign domain.

The OpenAPI golden covers the `/crm/campaigns` subtree only. Other root CRM routes, user-defined host prefixes, server metadata, unrelated integration schemas and generated OpenAPI operation IDs are **intentionally not frozen** here.

This is a **selective contract snapshot**, not a full raw OpenAPI document. It protects path/method inventory, exact declared response status sets, the response's schema family and request body DTO names. Other OpenAPI details remain to be reviewed as warranted by LOT-31-004/005.

## 3. Current HTTP contract

- Campaign routers are **opt-in** and require an explicit host-configured security boundary.
- 22 FastAPI Campaign operations are grouped as metadata/lifecycle (7), audience/Segment sources (9), and attribution/Communication links (6).
- Read/search pages expose `items`, `limit`, `offset`, `total`, `has_next`, `has_previous`; default `limit=50`, maximum `200`.
- Create uses 201; Segment source attach and attribution/Communication link creation also use 201. Ordinary reads, updates, lifecycle commands and removals use 200.
- FastAPI's Campaign root routes explicitly document 401/403 and framework request validation. Subresource routes additionally declare the existing list/mutation error response contracts, including 500 and, for mutations, 404/409.
- DRF uses the same domain semantics but does not natively publish a FastAPI OpenAPI document; it is qualified here through rendered JSON and explicit request/response checks.

**Important:** a domain conflict may return 409 even where an operation's generated OpenAPI currently does not explicitly document that response. The golden captures the *existing b3 document* and separately tests actual runtime errors; it does not silently add declarations to runtime code. Any decision to expand error documentation requires a reviewed compatibility correction.

## 4. Normalization rule

Real response comparison converts only these generated **values**:

- Valid UUID under JSON key `id` -> `<uuid>`.
- Timezone-aware ISO 8601 timestamp under `created_at` or `updated_at` -> `<utc>`.

The test retains **all** JSON object keys, nested object shapes, `null`, `revision`, `status`, `description`, `metadata`, order, pagination and all other stable values. Unexpected application keys or missing required keys cause a failure.

Golden scenario:

1. Create a named Campaign via real FastAPI HTTP (201).
2. Retrieve the same record through both adapters (200), compare against a reviewed Campaign object.
3. List via FastAPI and DRF; compare exact expected pagination object.
4. Clear `description` with a DRF PATCH, preserving explicit `null` and checking revision increment; read with FastAPI.
5. Exercise authorization/invalid input and stale version failures independently.

## 5. Error and privacy matrix

| Case | Expected HTTP status | Expected payload contract |
|---|---:|---|
| Forged unsigned actor header without host identity | **401** | `detail` only; no record information |
| Explicit denial of `campaign.members.read` | **403** | No audience `count` or `total` |
| Unknown valid Campaign UUID | **404** | `code=campaign.not_found`; `code/message/context` |
| Stale `expected_revision` | **409** | `code=campaign.revision.conflict`; no state mutation |
| Unrecognized PATCH `status` field | **422** | `code=request.validation_error`; no lifecycle bypass |

The error checks require the stable top-level `code`, `message` and `context` structure for domain and request validation errors. The internal structure of validation `context.errors` may differ between FastAPI and DRF: semantic error codes and statuses are frozen here, not incidental framework-specific error wording.

**Scope boundary:** these tests do not by themselves prove true multi-tenant isolation or the absence of a host authentication bypass. Those are release-blocking LOT-31-004 duties, including denial before access to facade/DB, external identity verification, and no post-pagination filtering.
