# PyCRMKit 1.2.0rc1 - LOT-31-014 Production Host Reference Journey

**Status:** candidate; qualify only after exact SHA CI.  
**Integration:** opted-in FastAPI Campaign routes + signed host principal, explicit tenant ownership guards, wheel-installed PyCRMKit + PostgreSQL 17 + packaged Alembic migrations.  
**Package version during this lot:** 1.2.0b3 (the actual 1.2.0rc1 version flip is exclusively LOT-31-015).

## 1. The host boundary is the product integration

PyCRMKit provides a headless CRM domain plus opt-in Campaign HTTP integration. It **does not** provide an identity provider, JWT validation, tenant IAM, request firewall, global rate limiter or durable event bus.

This example implements *host-owned* security for a **disposable integration environment**:

1. A bearer token issued by the **test scenario only** contains issuer, audience, subject, tenant, role, issued-at and 15-minute maximum expiry.
2. The **host application** validates a SHA-256 HMAC signature with a random signing secret provided by `PYCRMKIT_RC_HOST_SIGNING_KEY` and rejects malformed, tampered, expired, future-dated, wrong-audience and unsigned tokens. `X-Actor-ID` is not authentication.
3. An explicit `CampaignSecurityBoundary` resolves the verified principal, authorizes each Campaign action and verifies persisted Campaign ownership against the host's tenant owner **before constructing a CRM facade**.
4. A minimal `create_campaigns_router` is mounted. The generic `create_crm_router` is **not** mounted because its Contact, Segment and other non-Campaign routes do not receive this host's tenant permissions by default.
5. Generic Campaign creation, owner-changing PATCH, direct-member writes, Segment-source writes, attribution writes and Communication links are **denied** through the generic router. This is intentional, because that router cannot authorize the ownership of *all referenced entities*.
6. The host exposes opt-in `/host/campaigns` operations for creation, Segment capture, direct import, bounded JSONL export, attribution and Communication links. Each uses the same verified `CampaignHTTPAccess`, then validates referenced Contact/Segment/Communication tenant ownership before calling the existing public CRM facade. The example obtains Campaign owner IDs from the signed tenant claim, never caller-supplied `owner_id`.
7. Segment capture explicitly validates each captured Contact's owner, not just the Segment's owner, before persisting a snapshot. It rejects audiences exceeding 1,000 references (reference host limit).
8. Communication references are linked to a pre-existing record; only link IDs/roles are returned. Actual content/addresses are never returned from the Campaign link endpoint. The scenario stores a **synthetic test-only tenant marker** on the host-created Communication record. A production host must instead verify ownership using authoritative IAM/tenant association, not trust arbitrary user-modifiable metadata.

**Security statement:** a valid HMAC-signed test bearer token exercises a *real signature verification step* and short expiry, but it is **not** an OIDC/JWT, refresh-token, revocation or enterprise IAM implementation. The reference host uses host-owned tenant policy; it does not add tenancy primitives to PyCRMKit.

## 2. Executable scenario

`examples/campaign_rc_host/host_app.py` contains only the embedding host code. `examples/campaign_rc_host/scenario.py` is the test-only token issuer and complete E2E driver; it is staged alongside the app **outside the checkout**. The script asserts the imported `pycrmkit.__file__` is not under the GitHub checkout and the installed package metadata equals the frozen release baseline.

The scenario provisions two signed tenants, Alice and Bob, and seeded Contacts, Segments, and Communication records (synthetic only), then verifies:

| Host journey | Expected proof |
|---|---|
| No token / forged `X-Actor-ID`, tampered MAC, expired or wrong-audience bearer | 401, no CRM facade call |
| Cross-tenant Campaign read, audience count or attribution list | 403, no CRM facade call and no count/total leakage |
| Cross-tenant list owner query | 403 before Campaign service; own owner page total only |
| Generic unscoped Campaign creation and owner-changing update | Denied even for authenticated principal |
| Authenticated Campaign create with server-derived tenant owner | 201 and correct persisted owner |
| Cross-tenant Segment attach / reference through generic route | Denied, no snapshot |
| Tenant-scoped static Segment captured through host route | One captured member, correct audience count |
| Mixed-tenant import with otherwise valid rows | Entire batch denied before first write |
| Two same-tenant members imported and replayed | 2 created, replay 0 created / 2 duplicates; captured/direct audience union is 2 |
| JSONL audience export, host-bounded to 1,000 entries | Two deduplicated records, no Communication contents |
| Cross-tenant attribution target and generic write | Denied; trusted target produces normalized source |
| Cross-tenant Communication record link and generic write | Denied; verified host-owned record links once, only reference returned |
| Destroy/recreate Engine and CRM facade | Same Campaign, count, attribution and Communication links persist |
| Other tenant after restart | Still denied |

**Caveats:** The local `StringIO` export response is bounded to a maximum audience of 1,000 by this demo route; large real workloads should wire a streaming file/blob destination to `export_campaign_records`. The imported 1,000-row limit is the library contract, and accepted rows commit individually: a database failure can leave an earlier valid prefix committed. Replays deduplicate **direct** members, not Segment captures. No exactly-once claim is made. The sample does not expose delivery/provider services.

## 3. Installed-wheel CI (real PostgreSQL)

New GitHub Actions workflow `.github/workflows/campaign-rc1-production-host.yml`:

```text
checkout exact PR SHA
  ↓
build wheel and sdist + twine check
  ↓
install wheel[fastapi,postgresql,migrations] in clean /tmp venv
  ↓
generate random test signing key in GITHUB_ENV (never committed or printed)
  ↓
apply wheel-installed pycrmkit-migrate upgrade head / check
  ↓
stage host_app.py and scenario.py under /tmp
  ↓
execute scenario with PYTHONPATH="" and independent installed wheel
  ↓
signed/tenant negative tests + full Campaign API journey + restart verification
```

The PostgreSQL 17 service is isolated and disposable. CI-only PostgreSQL uses `POSTGRES_HOST_AUTH_METHOD=trust` on a dedicated throwaway service to avoid storing test database passwords in Git history; **this must never be used in a real host**. A deployed host requires authenticated TLS database access and a secret-managed connection URL. The workflow does not run an external public network server, use real users, access production secrets, tag, publish PyPI or merge branches. The FastAPI TestClient traverses an ASGI host with real HTTP request/response handling and a real PostgreSQL backend; it is not a network latency benchmark.

The other transport, **Django REST Framework**, retains a separate equivalent security contract under `tests/integrations/drf/test_campaign_host_scope_rc.py` and the `Public API Freeze`/DRF CI workflows, qualified in LOT-31-004/005. This LOT does **not** claim the DRF-host exact same configured application is running or that two transports share one migration schema.

## 4. Reproduction

With a *throwaway* PostgreSQL service (never point this demo at a production DB):

```bash
python -m build
python -m venv /tmp/pycrmkit-rc1-host-venv
/tmp/pycrmkit-rc1-host-venv/bin/python -m pip install \
  "dist/pycrmkit-1.2.0b3-py3-none-any.whl[fastapi,postgresql,migrations]" \
  "httpx>=0.28,<1"
export PYCRMKIT_DATABASE_URL='postgresql+psycopg://.../throwaway_db'
export PYCRMKIT_RC_HOST_SIGNING_KEY="$(python -c 'import secrets;print(secrets.token_hex(48))')"
export PYCRMKIT_EXPECTED_VERSION='1.2.0b3'
PYTHONPATH="" /tmp/pycrmkit-rc1-host-venv/bin/pycrmkit-migrate upgrade head

mkdir -p /tmp/pycrmkit-rc1-host-reference
cp examples/campaign_rc_host/*.py /tmp/pycrmkit-rc1-host-reference/
cd /tmp/pycrmkit-rc1-host-reference
PYTHONPATH="" /tmp/pycrmkit-rc1-host-venv/bin/python scenario.py
```

For local-only reproduction the scenario requires `GITHUB_WORKSPACE` as checkout-root provenance guard (CI sets it); set it to the checkout path explicitly outside GitHub Actions.

## 5. Scope and residual risks

- No built-in authentication, tenant model, cross-contact IAM or OIDC provider is added to PyCRMKit. Application owners must implement production identity verification, roles and entity ownership consistently for **all** generic CRM routes they expose.
- The host's `owner_id = UUIDv5(tenant)` mapping is deterministic test scaffolding, **not a secure external directory of tenant IDs**. Real hosts use an authoritative tenant registry and database row scoping; the demo's pre-authorizer SQL ownership lookup intentionally accesses PostgreSQL, not the CRM facade.
- Reference HMAC token signing is deliberately minimal and not a standard OAuth token scheme. Actual secure deployments need session/key rotation, revocation, token audience and issuer management, TLS termination, rate limiting, trusted proxy configuration and abuse monitoring. The secret is generated at CI runtime and never lives in this repository.
- The example does not enforce durable outbox, DLQ, multi-region failover, PII retention/deletion, production-grade logging or operational SLAs. Full security and observability admission remain the application host's responsibility.
- Any correction after LOT-31-014 must rerun all workflows on the new exact SHA. Change the package source version to `1.2.0rc1` only during LOT-31-015, then repeat the installed-wheel E2E against that **actual RC artifact** before LOT-31-016 publication decision.
