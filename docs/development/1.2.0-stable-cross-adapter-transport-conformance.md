## Architectural objective

The same observable CRM-facing Campaign contract must hold across three independently qualified persistence adapters and both optional HTTP transports. This applies **Ports & Adapters**, **Dependency Inversion**, **Repository/Unit of Work**, **Contract Testing**, and **separation of domain versus host security**.

| Contract | Memory | SQLAlchemy + PostgreSQL 17 | Django + PostgreSQL 17 | FastAPI/DRF |
|---|---|---|---|---|
| Direct membership import/replay (CSV/JSON/JSONL) | Test | Test | Test | Pure Python boundary |
| Captured Segment source stays separate from direct import | Test | Test | Test | Existing HTTP parity |
| Export audience/direct/sources and canonical privacy | Test | Test | Test | No file HTTP endpoint |
| Revision, archival, error-code and no false event | Test | Test | Test | 409/403/404/422 parity |
| Same facades and stable DTO/HTTP payloads | Existing RC suite | Existing RC suite | Existing RC suite | Existing RC suite |
| Database migrations and transactions | Previously qualified | Previously qualified | Previously qualified | Not a transport responsibility |

SQLAlchemy and Django run against **different disposable PostgreSQL 17 databases**. Memory is not used to claim concurrency, durability or PostgreSQL compatibility. The CI checks a JUnit report for **zero skipped tests** and meaningful coverage of each named adapter; lack of a database is a **NO-GO**, not a pass on SQLite or mocks.

## Boundaries and residual risks

- `import_campaign_members` **does not** provide file-wide atomicity or durable distributed exactly-once; accepted rows commit individually and replay deduplicates known direct membership.
- Offset-paginated exports do not guarantee a point-in-time snapshot while writers mutate membership or Segment sources.
- Direct Python entrypoints inherit **no implicit HTTP authentication, tenant isolation or authorization**; the consuming host owns these checks.
- Django supports Campaign Communication linkage metadata, **not** full email-delivery repository parity.
- Synchronous post-commit events do not imply a durable outbox or exactly-once delivery.
- PostgreSQL 16/17 concurrency and Django/Alembic migration ownership remain governed by LOT-32-004; this lot validates semantics in PG17, not new multiwriter race guarantees.
