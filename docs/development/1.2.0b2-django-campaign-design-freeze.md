## 2. Decision CAMP-DJ-005: Django source identity

**Decision: accepted for the design.**

- Represent `CampaignSegmentSourceModel` with an internal `BigAutoField` primary key `id`, plus database uniqueness on `(campaign_id, segment_id)`.
- Represent `CampaignSegmentMemberModel.source` with a real, database-constrained `ForeignKey` to the source row, plus uniqueness on `(source_id, entity_kind, entity_id)`.
- Set `db_constraint=True`; prohibit `ForeignObject` or an unprotected pair of string columns.
- Model the source's `campaign` as a real FK to `CampaignModel`, and apply the same ownership rule to all other Campaign children.
- Keep the technical source/child row ids out of the domain and the public repository Protocols. Hydrate the business key from `source.campaign_id` and `source.segment_id`.
- Segment, Communication and CRM entity references remain scalar ids without cross-aggregate FKs.
- Use `on_delete=models.CASCADE` for Django ORM ownership deletion.

**Important qualification:** Django 5.2's `on_delete=models.CASCADE` is an ORM-level policy, **not** by itself a PostgreSQL DDL `ON DELETE CASCADE` action. The ordinary FK ensures database integrity (orphan insertion rejected), while deleting parent records via Django ORM cascades through Django's deletion collector. Do not claim database-native cascade unless the generated PostgreSQL DDL is inspected and deliberately extended.

**Why not the SQLAlchemy composite PK?** Django 5.2 supports `CompositePrimaryKey`, but `ForeignKey` cannot target one, and the `ForeignObject` workaround does not create DB FK constraints or indexes. The surrogate is internal only; observable Campaign semantics and business key stay identical.

Documentation: https://docs.djangoproject.com/en/5.2/topics/composite-primary-key/ and https://docs.djangoproject.com/en/5.2/ref/models/fields/#django.db.models.ForeignKey.on_delete

## 3. Decision CAMP-DJ-015: schema ownership and table naming

**Decision: accepted for the design.**

Retain the planned six names, for compatibility of vocabulary, **not** as a guarantee of interchangeable physical schemas:

```text
pycrmkit_campaigns
pycrmkit_campaign_members
pycrmkit_campaign_segment_sources
pycrmkit_campaign_segment_members
pycrmkit_campaign_attributions
pycrmkit_campaign_communication_links
```

On SQLAlchemy b1, the source uses composite PK `(campaign_id, segment_id)`, and its member uses a composite FK. Under Django b2, the source has a surrogate PK and its member references `source_id`. These are **physically different schemas despite matching table names**.

A single set of Campaign tables must not be independently migrated by Django and Alembic. Qualification uses separately provisioned test databases or schemas with exclusive migration ownership. No data migration from SQLAlchemy to Django is promised. If an integrator needs a shared DB/schema, require a later formal mapping/data migration and DDL audit.

## 4. Decision CAMP-DJ-017: Communication repository capability

**Status: BLOCKING / unresolved scope decision. Do not declare full façade parity.**

Inspected b1 source:

```text
CampaignsAPI._linkage_service(uow)
  -> CampaignLinkageService(
       uow.campaigns,
       uow.campaign_linkage,
       uow.communications,    # absent from DjangoTransactionBridge
       uow.segment_query_executor,
     )
```

`CampaignLinkageService.link_communication()` calls `CommunicationRepository.get_record()` to validate existence. `communications_for_campaign()` also fetches records from that repository. Even `add_attribution()` and `attributions()` currently pass through the same eager service construction, so simply adding the Campaign repositories would otherwise expose an `AttributeError`.

### Scope alternatives

**A. Native full parity (necessary to claim full public parity).** Add a bona fide, transactional Django `CommunicationRepository` and the needed ORM persistence/migration support. The existing Protocol covers more than `get_record`: intents, attempts, records and delivery events. This is a real additional scope, needing its own implementation plan, migration dependency ordering and tests. Do not silently add the required tables to Campaign `0004`.

**B. Bounded b2 parity (safe interim, NOT full façade parity).** Internally decouple the linkage service wiring so attribution and link listing/removal work with Campaign repository capabilities alone; methods requiring Communication existence or record lookup fail with a stable `IntegrationError` when the Communication capability is absent. Never bypass `get_record()` during link creation. This needs dedicated tests and release notes explaining the limitation.

**C. Integrator-supplied repository.** Permissible only with proven record existence, same-transaction behavior, consistent isolation and rollback. Cross-store lookups do not prove these properties by default.

**Gate decision:** Until the product owner explicitly chooses A/changes scope or explicitly narrows the published milestone contract and acceptance criteria to B, the 1.2.0b2 **full-parity release gate is NO-GO**. B can be used as a safe implementation increment, never as evidence of full parity. No fabricated Communication record, no invented `communications` bridge property and no unhandled `AttributeError`.

## 5. Remaining mapping decisions

| Concern | Plan | Qualification |
|---|---|---|
| Campaign root | String UUID PK, key unique, revision >= 1, UTC timestamps, JSON metadata | Model checks + domain codec |
| Direct member | Unique `campaign + entity_kind + entity_id` | Duplicate on PostgreSQL |
| Segment source | Unique `campaign + segment_id`, internal PK | Negative FK + multi-source snapshot |
| Captured member | FK `source`, unique `source + kind + id` | Negative FK, ORM cascade |
| Attribution | `external_ref` non-null, encode `None` as `""` | Unique constraint and race |
| Communication link | Unique `campaign + communication_id`; no Communication FK | Link contract and capability gate |
| Campaign update | Conditioned `UPDATE WHERE pk AND revision` | Two-writer PostgreSQL CAS |
| Audience | DB-side UNION DISTINCT and DB-side page/count | Deterministic pagination / SQL examination |
| Transaction | Existing bridge's `atomic` and `on_commit` | Nested rollback never emits events |
| Error mapping | Domain error classes/codes equal Memory and SQLAlchemy | Cross-backend contract suite |

Use explicit short (< 63-character PostgreSQL limit, preferably <=30-character Django convention) constraint/index names. Migration names and index names will be verified by `makemigrations --check --dry-run` and PostgreSQL introspection.

## 6. Required feasibility experiments before closing LOT-29-001

The initial Django model/FK/uniqueness and migration regression test code has been committed; execution evidence is **pending**. The remaining experiments must run against real PostgreSQL 17, not only SQLite, **before** `0004` is accepted as frozen.

1. **FK negative:** Insert a captured member with a nonexistent `source_id` inside `atomic()`; expect a database `IntegrityError` and zero rows committed. Confirm the source FK exists in PostgreSQL catalog.
2. **ORM deletion:** Create Campaign -> Segment source -> 2 captured members; call `source.delete()` through Django ORM; source and captures disappear together, direct members remain intact.
3. **Raw SQL deletion:** Inspect constraint `confdeltype` and exercise raw parent deletion in a rolled-back transaction. Record whether DB-level cascade or restrict/no-action occurs; do not confuse ORM cascade with DB cascade.
4. **Business key:** Two sources with identical `(campaign_id, segment_id)` must conflict; reuse the same segment in another campaign must work.
5. **Migration fidelity:** Run `0003 -> 0004 -> 0003 -> 0004` with historical rows; `makemigrations --check --dry-run` must be clean.
6. **Communication contract:** Execute all `crm.campaigns` linkage methods with the Django bridge. Fail closed with `IntegrationError` if B is chosen; if A is chosen, require full native existence validation and same-transaction behavior.
7. **Adapter isolation:** Run Memory, SQLAlchemy and Django contract fixtures separately; confirm no schema is managed by two migration systems.

Models and the draft migration are present on the feature branch for qualification. **No merge, schema freeze or `1.2.0b2` package version promotion is authorized** until design gates and relevant CI/PostgreSQL checks pass.

## 8. CommunicationRecord narrowing for Campaign linkage (2026-10-28)

**New implementation decision:** The native Django
`DjangoCommunicationRecordStore` persists and hydrates the complete
`CommunicationRecord` domain object, including counterparties, entity
references, metadata, timestamps and typed IDs. It participates in the same
`DjangoTransactionBridge` transaction as Campaign, Audience and Linkage.
It validates existence in `crm.campaigns.link_communication()` and returns
actual domain records in `crm.campaigns.communications()`.

- `0004_campaign_persistence` remains six Campaign models.
- New additive `0005_communication_record_store` owns the Communication
  record table. This is not part of the original six-table migration.
- **Not delivered:** Full Django `CommunicationRepository` (intent, delivery
  attempt and delivery event methods). The new adapter is a narrow
  `CommunicationRecordLookup`, not a full Communication subsystem.
- The fail-closed `IntegrationError` remains for adapters with no record
  lookup. No non-existent Communication record can be linked.
- Django integrators can save actual records using
  `DjangoTransactionBridge.communications.save_record()`. No email sending
  engine or HTTP endpoint is introduced by this milestone.
- PostgreSQL qualification of the schema, transaction boundaries,
  migration and installed wheel is required before any stable claims.

**Verdict:** full **Campaign method** parity is technically possible via a
real Django record store. This does **not** imply full cross-domain
CommunicationRepository parity.
