## 1. Intent

Expose the already-existing `crm.campaigns` attribution references and CommunicationRecord link metadata through optional, secured FastAPI and DRF transports. This milestone **does not** implement campaign delivery, a Communication CRUD API, or a provider messaging pipeline.

The HTTP integration is opt-in, and requires verified host identity and action/resource authorization. `X-Actor-ID` is never accepted as proof of identity. All operations call `crm.campaigns`, and no transport accesses ORM models or repositories directly.

## 2. Logical routes

| Method | Path relative to /crm | Action | Response |
|---|---|---|---|
| GET | `/campaigns/{campaign_id}/attributions` | `campaign.attribution.read` | `Page[CampaignAttributionResponse]` |
| POST | `/campaigns/{campaign_id}/attributions` | `campaign.attribution.write` | 201 + attribution metadata |
| POST | `/campaigns/{campaign_id}/attributions/remove` | `campaign.attribution.write` | 200 + `{"removed": bool}` |
| GET | `/campaigns/{campaign_id}/communication-links` | `campaign.communications.link` | `Page[CampaignCommunicationLinkResponse]` |
| POST | `/campaigns/{campaign_id}/communication-links` | `campaign.communications.link` | 201 + link metadata |
| POST | `/campaigns/{campaign_id}/communication-links/remove` | `campaign.communications.link` | 200 + `{"removed": bool}` |

DRF uses its normal trailing-slash style. FastAPI uses paths without trailing slash. Host applications own the outer `/crm` prefix.

Neither transport registers these endpoints by default; they are only enabled through the b3 Campaign opt-in router and verified security boundary.

**No** `GET /campaigns/{campaign_id}/communications` is registered. The full content of a CommunicationRecord can contain sensitive customer information and must not be exposed through metadata-only permission.

## 3. Wire contract examples

### Add attribution

```json
{
  "target": {"kind": "contact", "id": "00000000-0000-4000-8000-000000000011"},
  "source": "LinkedIn",
  "external_ref": "utm-2026-q4",
  "metadata": {"channel": "social"}
}
```

The domain normalizes `source` to lowercase/space-normalized form and trims `external_ref`; the HTTP DTO exposes the resulting persisted values. Only supported segmentable CRM entity kinds are permitted. All target existence and mutability checks remain owned by the domain service.

### Link an existing communication

```json
{
  "communication_id": "00000000-0000-4000-8000-000000000021",
  "role": "touchpoint",
  "metadata": {"purpose": "renewal"}
}
```

The service requires a **real existing CommunicationRecord** through the configured backend capability. A random UUID cannot create or stand in for a CommunicationRecord.

Response fields are strictly limited to:

```json
{
  "campaign_id": "00000000-0000-4000-8000-000000000031",
  "communication_id": "00000000-0000-4000-8000-000000000021",
  "linked_at": "2026-10-28T17:00:00Z",
  "role": "touchpoint",
  "metadata": {"purpose": "renewal"}
}
```

The timestamp above is illustrative. The transport never serializes `subject`, `counterparties`, message body, delivery events, or `actor_id` as part of the link response.

## 4. Security and error handling

- Unauthenticated request: **401**, including attempts to impersonate another actor via `X-Actor-ID`.
- Authenticated but unauthorized action or Campaign: **403** before any data/count is returned.
- Nonexistent Campaign/CommunicationRecord: domain NotFound mapping **404**, without inventing link records.
- Invalid UUID, request JSON shape or pagination: **422**.
- Conflict/invalid lifecycle: existing domain conflict mapping **409**.
- Unavailable configured persistence capability: existing public integration error contract; no fictional successful link.
- List reads are bounded by `OffsetPageRequest` (default 50, max 200).
- Metadata is constrained by the common 16 KiB and nesting-depth validation.
- No arbitrary CommunicationRecord subject/body/person data in response or errors.

### Link metadata caveat

The `campaign.communications.link` permission currently covers link metadata read/write, not content read. A later revision may split link read/write into separate action names if the host needs least-privilege policies at finer granularity. That is a future contract change and requires tests and documentation.
