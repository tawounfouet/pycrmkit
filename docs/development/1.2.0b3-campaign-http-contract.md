## 1. Rules common to FastAPI and DRF

- Host owns outer prefix, commonly `/crm`; module owns `/campaigns`.
- The same JSON keys, semantic types, HTTP statuses and error codes must be observed for both transports.
- UUID values serialize as strings. Time values use aware ISO 8601 UTC serialization (the chosen lexical form must match exactly in parity tests).
- Entity reference on HTTP uses existing `EntityReferenceSchema` shape `{"kind":"contact","id":"<uuid>"}`. **CSV/JSON/JSONL import** uses `entity_kind` / `entity_id` column names, deliberately a separate flat record shape.
- `limit` defaults to 50, maximum 200; `offset >= 0`; `PageResponse` keys: `items`, `limit`, `offset`, `total`, `has_next`, `has_previous`.
- The host must inject a verified principal and authorization policy. `X-Actor-ID` has no authentication standing; `X-Correlation-ID` is only validated trace metadata.
- Query and request JSON unknown fields are rejected when explicitly defined by contract. Object identifiers in paths must be valid UUIDs.
- No DB models, queries, secrets or unredacted CRM payloads in responses, audit metadata or error details.

## 3. DTO catalogue

### 3.1 Campaign metadata

- `CampaignCreateRequest`: `key: str`, `name: str`, optional `description: str|null`, `starts_at: aware datetime|null`, `ends_at: aware datetime|null`, `owner_id: UUID|null`, `metadata: JSON object`. No client-provided status/revision/timestamps.
- `CampaignUpdateRequest`: required `expected_revision: positive int`, optional `name`, `description`, `starts_at`, `ends_at`, `owner_id`, `metadata`. **Presence matters**; no `status` or `key`.
- `CampaignRevisionRequest`: required `expected_revision: positive int` for `activate/complete/archive`.
- `CampaignResponse`: `id`, `key`, `name`, `description`, `status`, `created_at`, `updated_at`, `starts_at`, `ends_at`, `owner_id`, `revision`, `metadata`, `archived_at`.
- Query: `status`, `owner_id`, `include_archived`, `limit`, `offset`; no new repository search operators.

```json
{
  "key": "renewal-q4",
  "name": "Renewal Q4",
  "description": null,
  "starts_at": null,
  "ends_at": null,
  "owner_id": null,
  "metadata": {"department": "sales"}
}
```

```json
{"expected_revision": 3, "description": null}
```

This PATCH clears description only and leaves every other metadata field unchanged. By contrast, `{"expected_revision":3}` makes no field change. The domain `CampaignUpdate.UNSET` is **not** exposed as a JSON token.

### 3.2 Audience and sources

- `CampaignMembersRequest`: `members: list[EntityReference]` of 1..1000, optional `source` and `metadata`; no repeated member identity in one request.
- `CampaignMemberResponse`: `campaign_id`, `entity: {kind,id}`, `added_at`, `source`, `metadata`; do **not** emit `actor_id` by default across public HTTP until redaction policy is proven.
- `CampaignSegmentAttachRequest`: `segment_id: UUID`, optional JSON `metadata`.
- `CampaignSegmentSourceResponse`: `campaign_id`, `segment_id`, `segment_revision`, `entity_kind`, `attached_at`, `captured_at`, `member_count`, `metadata`.
- Remove-members request reuses the same reference list shape, but empty-list policy must be explicitly tested; output `{"removed": integer}`.
- Audience response is `Page[EntityReference]`; `audience/count` is `{"count": integer}`. The UNION of explicit and captured members does not assign a single origin to merged identities.

### 3.3 Attribution and communication linkage

- `CampaignAttributionRequest`: `target: EntityReference`, `source: str`, `external_ref: str|null`, `metadata: JSON object`.
- `CampaignAttributionResponse`: `campaign_id`, `target`, `source`, `external_ref`, `recorded_at`, `metadata`.
- `CampaignCommunicationLinkRequest`: `communication_id: UUID`, optional `role` (default `touchpoint`), `metadata`.
- `CampaignCommunicationLinkResponse`: `campaign_id`, `communication_id`, `role`, `linked_at`, `metadata`; omit `actor_id` by default.
- `unlink` must not invent a missing record; **link** must verify a real existing `CommunicationRecord` through supported capability.

## 4. Error and security matrix

| Condition | HTTP | Evidence to implement |
|---|---:|---|
| No trusted authenticated principal | 401 | Deny absent/forged token and unsigned `X-Actor-ID` |
| Authenticated, policy refuses action/object/scope | 403 | No data/count/metadata leak |
| Missing Campaign, Segment or required CommunicationRecord | 404 | Domain/not-found code preserved |
| Invalid UUID, unrecognized field, naive datetime, invalid page | 422 | Same schema meaning |
| Stale revision, duplicate constrained resource, invalid lifecycle | 409 | No partial update |
| Adapter required capability unsupported | Existing safe IntegrationError mapping | Never fake success |
| Unhandled internal failure | 500 sanitized | No stack trace or record body leaked |

**Authorization and error precedence:** a denied object may intentionally return 403 (or concealed 404, with a deliberate documented policy) without revealing existence. Choose one consistent contract at the security integration gate. The host is responsible for rate limiting.

## 5. DataOps records (Python-only initial b3 scope)

```json
{"entity_kind":"contact","entity_id":"00000000-0000-4000-8000-000000000001"}
```

- Import receives trusted target `campaign_id` from operation config; does not allow a row to redirect to another Campaign.
- Direct-member export: `campaign_id`, `entity_kind`, `entity_id`, `source`, `added_at`; actor field omitted unless explicitly authorized.
- Deduplicated-audience export: `campaign_id`, `entity_kind`, `entity_id`.
- Segment-source export: `campaign_id`, `segment_id`, `segment_revision`, `entity_kind`, `attached_at`, `captured_at`, `member_count`.
- No automatic export of CommunicationRecord content; no upload/download endpoint in the default b3 scope.
- CSV/JSON/JSONL must produce equivalent data with deterministic field ordering and stable pagination under unchanged data. Multi-page export is **not** automatically a transaction-consistent snapshot.
