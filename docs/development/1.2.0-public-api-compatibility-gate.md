## 1. Purpose and architecture

**Goal:** guarantee the observable public Campaign metadata, V1 CRM and V1.1 segmentation behavior while preparing the 1.2 stable release. No feature, entity, migration, producer, provider integration, or public API may be added by this lot.

**Design approach:**
- **Consumer-driven contract tests** and golden fixtures; no regeneration of versioned historical snapshots.
- **Semantic Versioning / PEP 440:** patch and minor stability are defined from the consumer's perspective, not arbitrary source internals.
- **Hexagonal / Ports & Adapters:** the core remains importable without Django/FastAPI/SQLAlchemy; HTTP uses optional, host-authenticated adapters.
- **CQRS boundary:** Campaign query/list/count cannot bypass host authorization; domain commands enforce revision and lifecycle policies.
- **Event-Driven Architecture:** 16 registered Campaign event types and V1 versioned domain-event envelope are public integration contracts.

## 3. RC → stable source comparison (not just runtime source tests)

The new CI workflow `.github/workflows/campaign-stable-compatibility.yml` performs both:

1. **Source identity:** `git rev-parse 'refs/tags/v1.2.0rc1^{commit}'` must equal `5113cedb50750185e457505dfcca5519ce3a62bd` and be an ancestor of the tested commit.
2. **Exact file-byte diff:** `git diff --exit-code RC_SOURCE HEAD --` over `src/pycrmkit/campaigns`, `src/pycrmkit/events`, `src/pycrmkit/facade/campaigns.py`, Campaign security and payload validation, optional FastAPI/DRF adapters, V1/V1.1/Campaign candidate public API manifests, and the Campaign HTTP OpenAPI/JSON golden fixtures.

This precisely detects any drift in the named code/fixtures since the published RC. It is *not* a complete binary comparison of two built distributions nor a proof that unselected repository paths are equal. LOT-32-010 will requalify the stable distributions and artifact bytes.

**Exception rule:** if LOT-32-003/004/005 finds a genuine blocking defect requiring a change to a protected source path, that change must be reviewed, documented with consumer impact and tests, and requalified from a candidate `1.2.0rc2` where appropriate. Only then may this exact-match gate be deliberately revised, with clear PR rationale. It may not be bypassed or silently altered to keep CI green.

## 4. Contract rules

- **PATCH:** `UNSET` means omitted, distinct from explicit `None`. Null-clearing allowed for nullable fields; nonnullable `name` and `metadata` rejects null over FastAPI/DRF.
- **Concurrency:** stale expected revision raises public `campaign.revision.conflict` with HTTP 409; rejected commands cannot mutate stored Campaign.
- **Archival:** `archived` is terminal; `campaign.archived` is stable and no metadata changes permitted afterward.
- **Serialization:** V1 `DomainEvent` envelope field order and schema version remain stable. Campaign event types preserve registration; the new test checks the observable payload shapes of `campaign.created`, `campaign.updated` and `campaign.archived`.
- **HTTP:** Campaign routes are opt-in. The real FastAPI/DRF golden suites guard request/response JSON shape, OpenAPI, 401/403/404/409/422, pagination and accepted bounds.
- **Information security:** deny before CRM factory access; list/count and CommunicationRecord metadata must not leak to unauthorized clients. The HMAC fixture/reference is not production authentication or global tenant isolation.
- **Adapters:** SQLAlchemy/PostgreSQL and Django ORM must continue to conform to their UoW contracts but the *dedicated* final persistence/migration gate is LOT-32-004.
- **DataOps:** current Python-only import/export public signatures remain; global atomic import, exactly-once replay, snapshot export and universal spreadsheet safety are *not* newly asserted.
