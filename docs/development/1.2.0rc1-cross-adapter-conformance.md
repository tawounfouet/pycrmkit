# PyCRMKit 1.2.0rc1 — LOT-31-011 Cross-Adapter Conformance

**Release:** 1.2.0rc1 qualification, source version remains 1.2.0b3  
**Status:** candidate pending exact-SHA CI qualification  
**Parent gates:** LOT-31-005, LOT-31-009, LOT-31-010  
**Code changes:** shared tests and CI only; no migration or public-domain API changes.

## 1. Verification principle

**One identical Campaign facade journey must pass unchanged** under:

1. `MemoryUnitOfWork` with a persistent `MemoryStore`, as an in-process reference (not a production concurrency oracle).
2. `SQLAlchemyUnitOfWork` backed by a real PostgreSQL 17 database, with a separate SQLAlchemy Session per facade call.
3. `DjangoTransactionBridge` backed by a *different* PostgreSQL 17 database, with its Django migrations applied.

These are independently executed parametrized tests, not mocked SQL methods or a SQLite replacement for PostgreSQL. The test framework compares a **semantic invariant** shared by all three adapters. UUIDs generated independently are checked for stable internal identity across reopen, but not falsely required to equal UUIDs from other backends.

Never point Alembic/SQLAlchemy table creation and the Django migration manager at the same physical schema. Django and SQLAlchemy Campaign source/snapshot FK mappings are intentionally different. The Django CI workflow provisions separate PostgreSQL reference-application, Django contract and SQLAlchemy conformance databases.

Memory and Django are additionally exercised on SQLite in the optional Django-only CI for portability, **without** claiming that SQLite is the PostgreSQL qualification.

### Communication capability boundary (not a false equality claim)

- **Memory:** in-memory Communication record persistence is available as part of its broader adapter.
- **SQLAlchemy/PostgreSQL:** relational Communication storage is available through the SQLAlchemy-backed CRM stack.
- **Django:** `DjangoCommunicationRecordStore` offers same-transaction record lookup/save for Campaign linkage. It does **not** implement the entire `CommunicationRepository` protocol or the equivalent full email-delivery workflow. The shared tests deliberately qualify **Campaign attribution**, not pretend that Django provides full Communication delivery parity.
- A Campaign-to-Communication link may only be created when the referenced Communication record exists. Authentication, inbound/outbound provider integrations, durable delivery and tenant authorization remain explicit host responsibilities.

## 3. CI reproduction

```bash
python -m pip install -e ".[django,drf,postgresql,dev]"

# The reference application's DB has its own independent schema:
export PYCRMKIT_DATABASE_URL='postgresql://pycrmkit:***@localhost:5432/pycrmkit_django'

# The Django test fixture must target its own migrated database:
export PYCRMKIT_DJANGO_TEST_DATABASE_URL='postgresql://pycrmkit:***@localhost:5432/pycrmkit_django_campaign_contracts'

# The SQLAlchemy Base.metadata schema must target a third physical database:
export PYCRMKIT_CROSS_ADAPTER_SQLALCHEMY_URL='postgresql+psycopg://pycrmkit:***@localhost:5432/pycrmkit_rc_cross_adapter_sqlalchemy'

pytest tests/integrations/django/test_campaign_cross_adapter_rc.py -q -rs
```

Provision databases, apply Django migrations and verify they are disposable **before** running tests; the Django fixture migrates/reverses its own schema, and the SQLAlchemy fixture creates/drops its own metadata tables. Do not use production credentials, tenants or databases for this gate. The CI does all provisioning within `.github/workflows/django-e2e.yml`.

A plain Django-only installation may run `pytest tests/integrations/django -q`; SQLAlchemy's parametrization is explicitly **skipped** without the `PYCRMKIT_CROSS_ADAPTER_SQLALCHEMY_URL` (or SQLAlchemy itself), rather than passing on a mock. Only the dedicated PostgreSQL CI provides a full three-backend conformance result.

## 4. Supported differences and risk boundaries

- Internal table shapes, FK constraints and primary keys differ by persistence ownership, while outward domain results should conform.
- PostgreSQL 16/17 / SQLAlchemy / psycopg concurrency and constraint matrices are separately proved in **LOT-31-009**; this lot checks the *same facade-level business workflow*, not a new two-writer stress test.
- Django's event publisher is delayed to the outermost Django transaction through `transaction.on_commit` when ambient; Memory and SQLAlchemy publish synchronously after their own successful commit. The shared gate tests a top-level commit and exception rollback only; ambient semantics belong to **LOT-31-010**.
- Offset pagination under concurrent churn is **not** a point-in-time snapshot (LOT-31-008). The cross-adapter test walks a stationary dataset.
- Host-level security, lifecycle authorization, multi-tenant scoping and secure production credentials are not supplied by the persistence layer (LOT-31-004/014).
- This milestone does not change public APIs, immutable migrations, supported version ranges, or introduce Django Communication delivery capabilities.
