## 1. Severity and governance

- **Critical:** potential unauthorized data access or committed-state corruption; blocks RC and stable until qualified.
- **High:** severe correctness, privacy or compatibility ambiguity that may prevent production adoption; unresolved material defects block GO.
- **Medium:** bounded and explicitly documented operational risk requiring tests, mitigations and acceptance by the release maintainer.
- **Low:** non-blocking enhancement; not expected to be introduced in this feature-frozen RC.
- **Owner:** role responsible for collecting evidence; issue assignees and accountable maintainer to be confirmed.
- **Status:** OPEN / IN QUALIFICATION / QUALIFIED / ACCEPTED WITH LIMITS / BLOCKED. All start OPEN.
- **Gate:** must cite an exact candidate SHA, CI run or test output and a decision. Human declaration alone is not sufficient.

## 3. Qualification and acceptance by risk

### R-01 - Host identity and tenant isolation

**Exposure:** Campaign relies on host-verified principal and resource/action/scope authorization. A forged unsigned actor header or post-pagination filtering may leak other tenants' audiences, existence or counts.

**Mitigation and test plan:** Build authenticated reference applications for both HTTP adapters. Use two isolated tenant contexts and negative tests for unauthenticated requests, forged X-Actor-ID, denied list, denied audience count, wrong resource and scope. Use spies to prove that the facade/DB and total are not accessed on refusal.

**Expected evidence:** HTTP 401/403, zero unauthorized state change or count, no bypass, host trust-boundary documentation, exact candidate SHA and CI URLs. **Decision:** OPEN / critical gate.

### R-02 - Import failure and replay

**Exposure:** member import is synchronous and commits per accepted member; an unexpected DB failure may leave earlier committed records. Neither file-level atomicity nor durable exactly-once is offered.

**Mitigation and test plan:** Shared CSV/JSON/JSONL corpus, 1,000/1,001 preflight boundary, invalid UUID, absent entity, duplicate direct member, Segment-only member, midway failure and file replay. Verify ImportReport counts and exception propagation.

**Expected evidence:** no fake successful result, no extra direct duplicates on replay, partial-import recovery playbook and limits documented. **Decision:** OPEN / high gate.

### R-03 - Real PostgreSQL concurrent writes

**Exposure:** two sessions can race on identical (campaign, kind, entity) keys or the same optimistic Campaign revision. Mocks of integrity exceptions do not qualify live races.

**Mitigation and test plan:** Synchronize two separate PostgreSQL sessions. Assert exactly one committed direct membership, accurate failure outcome, stale revision conflict, rollback integrity, no lost update. Run in supported SQLAlchemy and Django integration paths without sharing physical migration ownership.

**Expected evidence:** committed database assertions, deterministic concurrency test logs, exact SHA, traceable CI run. **Decision:** OPEN / critical gate.

### R-04 - Export under churn

**Exposure:** offset pagination across pages does not guarantee a transactionally consistent snapshot if the member set is mutated concurrently.

**Mitigation and test plan:** Capture stable-order export baseline; introduce concurrent inserts/deletes between pages and characterize possible omissions/duplicates, without promising an impossible snapshot. Specify consumer mitigation such as snapshotting in a host-owned transaction/job if needed.

**Expected evidence:** tests showing real limitations, documented consistency contract and no unfounded snapshot claim. **Decision:** OPEN / accepted bounded risk only with explicit evidence.

### R-05 - CSV and personal data

**Exposure:** attacker-controlled cells may be interpreted as formulas when opened in a spreadsheet; Campaign export identifiers and provenance may be privacy-sensitive.

**Mitigation and test plan:** Evaluate every client-controlled exported string, including source, for prefixes =, +, -, @, tab and carriage-return. Choose and test a CSV-safe consumption/escaping policy consistent with published contract. Verify exported field allowlist, log redaction, authorization, retention and safe storage guidance.

**Expected evidence:** negative formula test corpus, no unexpected secrets/PII or Communication body/actor in exports, host retention obligations. **Decision:** OPEN / high gate.

### R-06 - HTTP and Python public contract drift

**Exposure:** FastAPI OpenAPI, Pydantic, DRF serializers, error mapping, package-level exports and V1 public import interfaces can drift unnoticed.

**Mitigation and test plan:** Freeze public facade signatures, values, events and error codes; record real OpenAPI route/shape snapshots and DRF golden JSON; verify null versus UNSET, pagination, 401/403/409/422, and actual installed wheel behavior.

**Expected evidence:** versioned golden fixtures and explicit classification of every change from b3; no unapproved breaking change. **Decision:** OPEN / high gate.

### R-07 - Unsafe host reference policy

**Exposure:** a simplistic allow-all authorizer could create false confidence that activating the Campaign HTTP routers automatically establishes tenant isolation.

**Mitigation and test plan:** Provide a working example with real verified host session/token, non-permissive action/resource authorization, scoped list decision and negative cross-tenant E2E against an installed distribution. Explicitly disallow promoting X-Actor-ID to principal.

**Expected evidence:** reference journey passing a deny-by-default policy with demonstrated 401/403 and non-disclosure. **Decision:** OPEN / high gate.

### R-08 - PyPI is a separate channel

**Exposure:** GitHub prerelease and verified wheel/sdist are not evidence of PyPI registration or registry availability. Docs must not claim otherwise.

**Mitigation and test plan:** Record an explicit publish/not-publish decision, require authorized publishing workflow and registry verification if approved, match version and binary fingerprint to qualified candidate bytes.

**Expected evidence:** separately evidenced PyPI state, or clear non-publication language. **Decision:** OPEN / medium gate.

### R-09 - Freeze and stable promotion

**Exposure:** new features, source/artifact retagging or a stable release built from unqualified code can invalidate the candidate's evidence.

**Mitigation and test plan:** Enforce scope freeze, blocker-only changes with justification, code review, complete candidate and exact-main CI, installed artifact checks, SHA256SUMS, manifest, annotated immutable tag and formal GO/NO-GO. A defect after rc1 triggers a new candidate when necessary.

**Expected evidence:** release decision tied to an exact SHA, audit of diff since final RC, correctly qualified artifacts and no late feature creep. **Decision:** OPEN / high gate.

## 4. Dependencies and execution order

1. LOT-31-001 registers risks and freeze. It does not resolve risks.
2. LOT-31-002/003 establish contract fixtures and reduce R-06.
3. LOT-31-004 and 31-014 qualify R-01 and R-07 through real host behavior.
4. LOT-31-006 to 31-010 qualify state/integrity, DataOps and real concurrency (R-02 to R-05).
5. LOT-31-011 to 31-013 provide adapter parity, performance and installed-artifact evidence.
6. LOT-31-015/016 finalize R-08/R-09, candidate release identity and final GO/NO-GO.

Blocking policy: any open **Critical** unmitigated risk is NO-GO; high-impact unqualified regressions, contract incompatibility, data leak or integrity violation are also NO-GO. A bounded medium risk may be **ACCEPTED WITH LIMITS** only with evidence and explicit documented ownership.
