# PyCRMKit 1.2.0rc1 - Campaign Security & Host Scope Qualification

**Work package:** LOT-31-004 - Security & Host Scope Qualification  
**Date:** 2026-10-29  
**Baseline:** v1.2.0b3 source 76aff8231ee4fe824088951af2e9ce20a0c54f68; RC workstream `feat/1.2.0rc1-production-qualification`  
**Version declaration:** still `1.2.0b3`  
**Status:** Test suites and CI gate added; **real host security and exact-SHA CI qualification pending**.

> This milestone tests PyCRMKit's security bridge and a **sample host policy**. PyCRMKit does not authenticate bearer tokens, provide a global IAM system or enforce implicit tenancy in its repositories. A host that resolves principals or authorizes scopes incorrectly can still leak data. Tests with synthetic bearer values or DRF `force_authenticate` are not proof of production JWT/session configuration.

## 1. Trust boundaries

```text
Untrusted HTTP request
  | forged X-Actor-ID, owner_id, campaign_id, filters, pagination
  v
Host authentication (JWT signature/session validation; external integration)
  | resolved, verified CampaignPrincipal(actor_id)
  v
CampaignSecurityBoundary.require(action, resource, scope)
  | reject absent principal (401), denied permission (403)
  | no call to CRM factory or facade on rejection
  v
Host CRM factory -> context-bound crm.campaigns facade
  v
Domain services -> repository / adapter / database
```

**Host-owned**: validate credentials against a real identity provider, bind a principal to a tenant, enforce per-action/per-resource authorization, force every list query into an authorized tenant scope, deny unscoped lists and defaults, maintain a reliable resource-to-tenant mapping, protect DataOps Python calls separately, protect **legacy non-Campaign routes** separately, audit privileges and segregate database access.

**PyCRMKit-owned**: Campaign routing is opt-in, requests invoke the explicit security boundary, a resolver must return `CampaignPrincipal` or `None`, authorizer must return literal `True`, invalid trace headers are replaced, and HTTP bridges should never construct the CRM from a denied request. The `X-Actor-ID` caller header is not an authentication credential in the Campaign endpoints.

## 2. Concrete threat scenarios and tests

| Threat / regression | Expected result | Test evidence |
|---|---|---|
| Forged actor header without verified identity | 401; zero calls to host CRM factory | FastAPI and DRF tests |
| Authenticated user requests another tenant's known Campaign ID | 403; zero calls to host factory | FastAPI and DRF tests |
| Cross-tenant PATCH | 403; original revision remains unchanged | FastAPI and DRF tests |
| Audience count or member listing for a foreign Campaign | 403; no returned totals or names | FastAPI and DRF tests |
| Unscoped `/campaigns` list | 403 *before pagination and before facade call* | FastAPI and DRF tests |
| User-supplied `owner_id` of another tenant | 403; zero calls to host factory | FastAPI and DRF tests |
| Legitimate tenant-scoped list with `owner_id` prefilter | 200; only owned Campaigns and correct total | FastAPI and DRF tests |
| Unknown/unauthorized Campaign action, even on own resource | Fail closed; 403 | Host policy fixture, FastAPI and DRF |
| Missing host principal must not call authorizer | 401 / `CampaignUnauthenticated` | Framework-neutral test |
| Policy returns truthy but not literal `True` | Denied | Framework-neutral test |
| Malformed or empty host principal | Invalid, no authorization | Framework-neutral test |
| Unsafe trace/header value | Ignored and replaced; never reflected as actor | Framework-neutral test |

The fixture uses **two Campaigns in one Memory CRM** with distinct `owner_id` values and a host-managed mapping `campaign_id -> verified tenant`. An allow decision for a list requires a client-supplied owner filter matching the authenticated tenant; otherwise the host denies the request **before database/facade access**. This illustrates a secure *pattern* but does not claim that `owner_id` by itself is an enterprise multi-tenant security primitive or that all endpoints are tenant-filtered automatically.

**Creation** is deliberately denied in this sample policy: the existing HTTP create endpoint accepts optional owner and no implicit tenant assignment. A production host must implement safe ownership assignment and authorization before enabling creation. Permissive/allow-all example policies are prohibited.

## 3. Files and CI

- `tests/unit/test_campaign_host_security_rc.py`: fail-closed return values, typed principals, anonymous rejection, trace-ID sanitation.
- `tests/integrations/fastapi/test_campaign_host_scope_rc.py`: real FastAPI `TestClient` with verified-principal and tenant-scope test double; asserts 401/403 before CRM factory and 200 for owned resources.
- `tests/integrations/drf/test_campaign_host_scope_rc.py`: real rendered DRF responses with host-supplied authenticated users, tenant object/scope authorization, 401/403 and pre-facade denial.
- `.github/workflows/public-api-freeze.yml`: new `Campaign RC1 Host Identity and Tenant Scope Qualification` step runs all three tests on the source checkout with dev extras.
- The pre-existing `tests/integrations/drf/test_campaign_http_golden_rc.py` was adjusted to avoid FastAPI hard imports in DRF-only extras. Ruff's unused `datetime.UTC` import was removed after previous CI failures. The cross-transport golden itself remains a dev-extras test.

Existing tests still cover opt-in route registration, policy requirements, forged actor headers, normal lifecycle, HTTP errors and authorized CRUD semantics. These new tests are **additive** and do not alter the public Campaign API, domain code, ORM schema, migrations or release version.

## 4. Remaining release-blocking checks

The following are **not qualified by LOT-31-004's synthetic host setup**, and remain required in LOT-31-014 or an explicit owner-approved production qualification gate:

1. Real host session/JWT verifier including signature, issuer/audience, expiration, revocation and credential rotation as appropriate.
2. Real per-tenant data access using production host mappings and storage, including host-wide and legacy routes.
3. Secure Campaign creation semantics: tenant ownership assignment independent of untrusted request payload.
4. Authorized python-only DataOps and external scripts, jobs, CLI and API caller contexts.
5. Owner-controlled resource associations and cross-resource actions: Segment snapshots, attribution and Communication links.
6. Audit logging, policy failure modes, exception logging and defense against telemetry leaks.
7. At least one real PostgreSQL host environment where authorization executes before SQL/ORM traffic.

**Blocking policy:** R-01 remains **OPEN / CRITICAL** and R-07 remains **OPEN / HIGH** until real-host tests and evidence are attached to an exact qualified SHA. No test-only fixtures may be advertised as deployment-ready authentication.
