A green RC prerelease is **not** stable approval.

### Exact evidence required

Before promotion or publication, record and cross-check:

1. Candidate PR head SHA, source diff from published RC, version and package metadata.
2. Python 3.11–3.13, PostgreSQL 16/17 and optional adapter/transport test matrix (real databases and clean wheels; avoid silent skips).
3. Lint, typechecking, `mkdocs build --strict`, security/privacy, performance and compatibility results on **the same exact candidate head**.
4. A maintainer-reviewed GO/NO-GO decision, effective branch rules, approvals, merge method and qualified merged `main` SHA.
5. Annotated tag's dereferenced source commit, publisher-only SHA when different, four **actual** release file sizes and SHA-256 checksums, plus SHA-256 after GitHub asset redownload.
6. An explicit **PyPI** decision: `NOT PUBLISHED`, `PENDING`, or `VERIFIED PUBLISHED` with independent evidence.

## Failed qualification / pre-publication recovery

1. **Do not merge/tag/publish** on a red gate, or claim that the failed run qualified the source.
2. Reproduce the failure against that exact SHA; classify security, API, packaging, docs, or infrastructure. Preserve the run links and root cause.
3. For changes to runtime behavior/API, review compatibility and whether a new `rc2` qualification cycle is necessary; never rewrite the `v1.2.0rc1` tag or its manifest.
4. Fix on the release branch in an auditable commit, rerun all applicable PR and push workflows against the **new SHA**, and replace the pending evidence report.

## Partial publication recovery (tag/release/assets)

- **Never move, replace or force-update an annotated stable tag**, a published RC tag or immutable release artifact to conceal a failure.
- If a candidate stable tag has already been created but release assets cannot be verified, **stop**. Record tag object, dereferenced target, asset list, checksums, publisher logs and user-visible status. Do not mark stable as published or claim PyPI availability.
- If tag target and qualified source differ, declare **NO-GO**, isolate the publication, escalate to the maintainer, and plan a separately approved corrective version; do not silently re-tag.
- If asset bytes mismatch manifest after download, quarantine the candidate assets, record incident and preserve evidence. Do not publish a new wheel over an immutable release under the same filename.
- If GitHub publication succeeds but PyPI is unavailable or unapproved, declare the **GitHub status accurately**, keep PyPI as `NOT PUBLISHED` or `PENDING`, and do not imply index availability.
- Do not change public docs to `PUBLISHED` until GitHub tag, release, actual uploaded assets, and their re-downloaded digests are verified in LOT-32-013. Delayed docs publication must not change the immutable tag's source.

## Ownership and support handoff

A consuming application owns IAM, cross-tenant authorization, privacy/retention, database credentials and backups, schema cutover, concurrent export consistency, operations logging and support incident response. The library provides typed CRM domain and optional adapters, **not a hosted CRM SLA or enterprise IAM**. See [support matrix](../reference/1.2.0-support-and-compatibility.md) and [upgrade runbook](../getting-started/1.2.0-upgrade.md).
