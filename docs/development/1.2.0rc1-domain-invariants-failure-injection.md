## 1. Contract source and boundaries

This lot qualifies **existing** behavior in the Campaign domain model, CampaignService, CampaignAudienceService, CampaignLinkageService, the transactional Campaign facade, and the MemoryStore / MemoryUnitOfWork.

The scope comes from the RC implementation plan: archived lifecycle, optimistic revision sequences, injected Unit of Work exceptions and events, `external_ref=None`, invalid inputs and nonexistent references.

**No domain API change, release-version change, or real PostgreSQL concurrency claim is made.** Tests use a fresh `CRM.memory(webhook_auto_delivery=False)` fixture except explicit memory fault-injection cases. The post-commit event dispatcher is synchronous and in-process, **not a durable outbox**.

## 2. Invariants and failure matrix

| Case | Existing expected behavior | Evidence |
|---|---|---|
| Complete a `draft` Campaign | `InvalidStateError`, `campaign.complete.invalid_state` | No revision increment or event |
| Activate a `completed` Campaign | `InvalidStateError`, `campaign.activate.invalid_state` | Completed state/revision unchanged |
| Repeat `activate`, `complete`, `archive` on the same state | Idempotent; no second revision increment or duplicate lifecycle event | Three distinct transitions and event counts |
| Stale revision on update, activate and archive | `ConflictError`, `campaign.revision.conflict` | `context.expected/actual` exact, no dirty write |
| Mutation after archival | `InvalidStateError`, `campaign.archived` | Metadata, member, attribution and link actions denied |
| Invalid name / temporal schedule / oversized description | Stable Campaign validation error codes | Existing record and audit state not changed |
| Missing CRM member target | `campaign.member.not_found` | No partial audience or event |
| Missing attribution target | `campaign.attribution.target.not_found` | No partial linkage or event |
| Missing Communication record | `communication.record.not_found` | No Communication linkage or event |
| Attribution with `external_ref=None` | Stored as `None`, same source/target/`None` duplicate rejected | `campaign.attribution.duplicate`; one event only |
| Empty attribution source | `campaign.attribution.source.required` | No persisted attribution or event |
| Ill-typed `CampaignUpdate.metadata=None` Python direct call | Current b3 raises Python `TypeError` | No partial Campaign update or event |
| MemoryStore exception **before** commit | Exception propagates; working state discarded | No Campaign/event, next transaction succeeds |
| Explicit Unit of Work rollback with staged event | Pending event discarded | No state committed; no event delivered |
| Event subscriber exception **after** commit | Subscriber exception propagates, **already committed Campaign remains** | No false rollback or exactly-once guarantee |

All covered error codes are derived from the current b3 implementation. No new error wording is invented to force test success.

## 3. Exact commit and publication boundaries

The MemoryStore commits a cloned working state and **then** dispatches staged domain events. Therefore:

1. **Domain validation failure / pre-commit store failure:** transaction state and staged events must be discarded; the facade must not report a successful write.
2. **Successful commit:** subscribers may observe committed Campaign state.
3. **Post-commit subscriber failure:** exception propagates, but the record was already committed. A caller retrying blindly could cause duplicates unless the host applies domain-specific recovery. Do not claim rollback, exactly-once delivery, durable replay or atomicity between MemoryStore commit and external event handlers.

These semantics are deliberately tested separately. Durable outbox, live DB commit failures and two-writer races belong to later lots, especially LOT-31-009. MemoryStore does not model concurrent writers.

## 4. Known input-validation boundary

The `CampaignUpdate.metadata` DTO advertises a `dict[str, object]` or `UNSET` type, but this alone does not enforce runtime types for direct Python callers. An ill-typed call such as `CampaignUpdate(metadata=None)` currently causes `TypeError` during conversion, not a stable `ValidationError.code`. The qualification test asserts **atomicity**, not a nonexistent business error contract.

FastAPI/DRF input schemas and serializers impose additional validation. Promoting runtime metadata type errors to new stable domain error codes would be a **reviewed compatibility correction**, not a silent RC test-side assumption.
