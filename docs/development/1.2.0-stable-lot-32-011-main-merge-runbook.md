1. Fetch PR #113, verify OPEN, base `main`, expected release branch and unchanged reviewed HEAD.
2. Check all PR-head GitHub Actions and **all paginated check-runs**. Every required check
   must conclude SUCCESS on the same SHA. Do not count older candidate SHAs.
3. Verify Python 3.11–3.13, PostgreSQL 16/17, installed wheel/sdist, FastAPI/DRF,
   security/privacy/GitGuardian, docs strict, typing, migrations, compatibility,

**Do not execute these commands while the decision is pending.**

```bash

  --json isDraft,mergeable,reviewDecision,headRefOid,baseRefOid,statusCheckRollup
```

the resulting main SHA will differ from the PR head and must be independently qualified.
Do not delete the release branch until evidence and recovery instructions are retained.

## 3. Post-merge exact-main qualification

1. Query `refs/heads/main` after the merge; record the **observed** merged SHA.
2. Verify `main` contains the intended `1.2.0` version and the exact reviewed diff;
   no concurrent main changes may be silently included.
3. Wait for the **push** workflow runs on that exact SHA (not PR merge-ref runs).
4. Page through all check-runs, verify no pending, failure, cancelled or skipped
   mandatory check. Require green global and dedicated Python/DB/host/distribution gates.
5. Rebuild and qualify wheel/sdist from exact main if the merge SHA or source tree
   differs from the PR candidate. Record immutable main source and artifact evidence.
6. Recheck that stable tag `v1.2.0` and GitHub stable Release are absent.
7. Record GO/NO-GO for the exact main SHA in PR #113. LOT-32-011 may close only
   after the controlled merge and green exact-main qualification.

## 4. NO-GO, failed merge or changed SHA

- Missing approval, unknown branch rules, unresolved blocker or failing check: **STOP**.
- HEAD or base changed after review: obtain fresh approval and full exact-SHA CI.
- Post-merge failure: **do not tag or publish**; record the failure and choose an
  approved forward fix or revert path, then fully requalify the new main SHA.
- A tag created prematurely must not be force-moved or hidden; escalate per
  [release recovery runbook](1.2.0-stable-release-gate.md).
- Never use the LOT-32-010 candidate hashes as final published-asset hashes.

## 5. Release separation

authorizes an annotated stable tag and exactly verified GitHub release assets.
