# PyCRMKit 1.2.0rc1 - LOT-31-012 Performance & Observability Gate

**Status:** candidate - qualification requires exact-SHA CI green.  
**Scope:** synthetic Campaign facade and authorized FastAPI HTTP, PostgreSQL 17, import 1,000 records, bounded paginated export, memory, anonymized SQL plans and error/output privacy.  
**Baseline:** existing V1 / 1.1 measurements in `docs/performance/baseline.md` and `benchmarks/performance_baseline.py` remain **unchanged**.

## 1. Goals and measurement integrity

The V1 performance budgets cover contact creation/search, timeline, generic import, repository pagination and event dispatch. They **do not measure Campaign HTTP, Campaign audience_count or Campaign imports/exports**. Do not compare unrelated per-contact/multi-tenant workloads as if they shared a measurable denominator. This LOT adds an independent **Campaign RC1 baseline**, and preserves the V1 source-and-installed-wheel benchmark gate without modifying its limits or reported history.

All measurements come from a synthetic fixed-size dataset, controlled version/runner environment, explicit fixtures, `perf_counter_ns()`, one warm-up and five repeats per read/replay/export operation. p50 is the sample median; p95 uses *nearest rank* (the maximum among five samples). They are empirical CI measurements, not prediction intervals, tail-latency SLAs or production capacity estimates.

| Scenario | Dataset | Samples | Platform | Metric |
|---|---|---:|---|---|
| Campaign `audience_count()` | 1,000 direct members | 5 | Memory; PostgreSQL | p50/p95 ms/call |
| Direct-membership `pre-scan` + duplicate replay | 1,000 existing direct members; 1,000 input rows | 5 | Memory; PostgreSQL | p50/p95 ms/replay; no writes |
| Paginated JSONL `export_campaign_records` | 1,000 direct rows; page size 100 | 5 + dedicated traced-memory probe | Memory; PostgreSQL | p50/p95 ms/export; traced Python peak MiB |
| First-time `import_campaign_members` | **1,000 new members** across three fresh Campaigns; backing Contacts exist | 3 plus warm-up Campaign | **PostgreSQL only** | p50/p95 ms/batch; counters exactly 1,000 created |
| Authenticated Campaign HTTP | GET Campaign and GET `audience/count` via FastAPI TestClient | 5 samples × 40 requests | Memory, host-owned bearer fixture | p50/p95 ms/request, 401 unauthorized check |
| PostgreSQL query profile | 10 repetitions of facade `audience_count` | 10 calls | PostgreSQL 17 | counted SQL statements (bound, not SQL text) |
| PostgreSQL `EXPLAIN` | `LIMIT 100 OFFSET 300` on direct Campaign members | 1 | PostgreSQL 17 | plan node *type names* and estimated rows; no raw SQL or parameter values |

**Pre-scan caveat:** the pre-scan/replay path deliberately exercises **only duplicate direct membership**; it is not a surrogate for new-member insertion throughput. The separate live PostgreSQL first-time import measures actual validated facade inserts and real per-row transaction commits. The in-memory fixture seeds its aggregate/membership data in one explicit UoW before measurements; fixture setup is excluded from timing. Python peak memory is measured around the paginated export alone.

## 2. Broad RC guardrails (not SLAs)

| Metric | CI release guardrail |
|---|---:|
| Campaign audience_count p95 | 500 ms |
| Direct pre-scan + 1,000-row replay p95 | 10,000 ms |
| JSONL paginated 1,000-row export p95 | 10,000 ms |
| First-time PostgreSQL 1,000-row import p95 | 180,000 ms |
| Traced Python export peak | 64 MiB |
| PostgreSQL audience_count on 10 calls | max 40 statements |
| HTTP in-process p95 | 500 ms |

No historical budget changed. The limits are intentionally broad to detect catastrophic changes on shared CI runners; the measured source/wheel p50/p95 values in the attached JSON artifacts, not these ceilings, form the future comparison baseline. A statistical/dedicated hardware regression test would need consistent hardware, OS, workload mix, cache and database setup, with a repeatable before/after control. Do not tighten guardrails silently.

The process `ru_maxrss` is recorded for the Linux runner, but no absolute process RSS gate is imposed on an unisolated shared runner. The export-specific `tracemalloc` peak is bounded to catch accidental aggregate materialization; this is Python-allocated memory, **not** all native SQL/driver allocations.

## 3. PostgreSQL query profile and explainability

The runner instruments SQLAlchemy `before_cursor_execute` on a *narrow scope*, counts statements executed by ten `audience_count` facade calls, removes the listener in `finally`, and checks a broad max. A parameterized, read-only `EXPLAIN (FORMAT JSON)` of a bounded Campaign membership page checks the query can be planned; evidence records only the tree's node types and top-level estimated rows.

No `EXPLAIN ANALYZE` or index-usage claim is made. With 1,000 rows, PostgreSQL may legitimately select a sequential scan; an index scan is observed but deliberately **not required**. Neither raw SQL text, bound UUIDs, credentials nor actual customer rows are persisted in artifacts. For real installations, the host should qualify plans and indexes using its realistic data volumes and query patterns.

## 4. Observability, audit and privacy

- Output files contain **only** version, runtime, backend label, fixed synthetic dataset sizes, aggregated measurements, guardrail verdict, bounded SQL statement count and sanitized plan node names; no email, contact name, UUID, request body, raw SQL, DB URL or bearer token.
- CI checks evidence structure and searches for UUID/email/credential patterns **before** uploading artifacts. JSON files are subject to normal GitHub Actions artifact access/retention policy.
- The HTTP probe registers an explicit **host-verified authorization boundary**, expects unauthorized requests to yield `401` and times only authenticated reads. Actor headers alone are not trusted. The benchmark does not enable permissive/allow-all Campaign access.
- `CRMConfig(events_enabled=False, audit_enabled=False)` is used for isolation in facade read/import benchmarks. This is **not** an audit trail qualification or proof that production logs are safe with arbitrary host middleware. Security refusal and response redaction belong to LOT-31-004; production audit, tracing and real host policies remain LOT-31-014.
- Event delivery is an in-process post-commit side effect, not durable observability. Failures from subscribers and recovery need host instrumentation; do not promise outbox/delivery SLAs.
- Campaign import pre-reads up to 1,001 rows to enforce a 1,000-row maximum, then commits accepted direct members individually. Failures can leave partial successful commits. Replay is deduplicated against *direct* members, never derived Segment snapshots.
- Offset exports over concurrently changing data are **not consistent snapshots** (LOT-31-008). Measured exports use a stationary synthetic dataset.

## 5. Reproducibility

```bash
python -m pip install -e ".[dev,postgresql,fastapi]"

python benchmarks/campaign_rc_performance.py \
    --backend memory --output campaign-rc1-memory-source.json
python benchmarks/campaign_rc_http.py \
    --output campaign-rc1-http-source.json

# Explicit throwaway PostgreSQL test instance, never production:
export PYCRMKIT_TEST_POSTGRES_URL='postgresql+psycopg://.../temporary_database'
python benchmarks/campaign_rc_performance.py \
    --backend postgres --output campaign-rc1-postgres.json
```

Run the existing V1 baseline with `python benchmarks/performance_baseline.py` for side-by-side evidence (its scenarios remain different). The **Performance Baseline** workflow repeats the core Memory test from a *core-only installed wheel* with `PYTHONPATH=""`; the HTTP probe runs from the source build with optional FastAPI installed. The **PostgreSQL** workflow runs real PostgreSQL performance/SQL-query tests, and uploads a separate anonymized JSON file. All three scripts exit with status 1 when a guardrail fails. No benchmark writes to or touches a live customer database.

## 6. Release gate and remaining risks

- Record the **actual** five-repeat p50/p95 JSON measurements and raw artifact links, exact workflow run ID and exact commit SHA before declaring this LOT qualified.
- Verify no green result relies on a skipped PostgreSQL test; the dedicated database URL must exist and the driver must be psycopg.
- Keep V1/1.1 budgets unchanged, preserve Campaign public signatures and migration history and keep PR #112 Draft.
- Known technical debt from LOT-31-011: SQLAlchemy `Session.flush(objects=...)` deprecation warning for Campaign Segment source insertion. It has not been counted as performance regression or silently suppressed.
- Host-wide real request tracing, audit fields, tenant authorization, data masking and realistic concurrency load are not implied by a synthetic TestClient or 1,000-row PostgreSQL CI test; those require LOT-31-014 production host proof.
