## 1. Canonical scope

The implementation plan for LOT-31-005 explicitly calls for:

1. End-to-end CRUD/lifecycle and member, Segment-source, attribution and Communication-link scenarios on resettable test data.
2. Mutations over FastAPI observed through DRF **and** the opposite direction, using one shared CRM facade/backend.
3. `expected_revision` stale-write conflicts, omitted values versus explicit `null`.
4. Offset pagination limit `1`/`200`, empty result pages and invalid upper/lower bounds.

This lot extends the existing `tests/integrations/test_campaign_transport_parity.py`, which already performs real FastAPI TestClient requests and fully rendered DRF APIRequestFactory/Response dispatch. The tests create a fresh `CRM.memory(webhook_auto_delivery=False)` for each scenario, preventing state leakage across tests.

## 2. Executable journey

| Scenario | First transport | Second transport | Assertion |
|---|---|---|---|
| Create Campaign A | FastAPI POST 201 | DRF GET 200 | Identical JSON, normalized timezone strings |
| Create Campaign B | DRF POST 201 | FastAPI GET 200 | Identical stored Campaign |
| Omitted PATCH | FastAPI PATCH | DRF read | `description` preserved; `revision=1` |
| Explicit `description: null` | DRF PATCH | FastAPI read | Cleared; `revision=2` |
| Stale expected revision | Both PATCH | Both reads | HTTP 409, same domain error code, no overwrite |
| Activate | DRF POST | FastAPI GET | `active`, `revision=3` |
| Complete | FastAPI POST | DRF GET | `completed`, `revision=4` |
| Archive | DRF POST | FastAPI GET | `archived`, `revision=5` |
| Add direct member | FastAPI POST | DRF GET | Total increases and entity visible |
| Remove direct member | DRF POST | FastAPI GET | Exact removed count and missing entity |
| Remove newly added member | FastAPI POST | DRF GET | Same remaining member list |
| Detach Segment snapshot source | DRF POST | FastAPI GET | Source page empty |
| Re-attach Segment source | DRF POST 201 | FastAPI refresh and DRF GET | Snapshot metadata and total consistent |
| Remove attribution | DRF POST | FastAPI GET | Attribution page empty |
| Add attribution | FastAPI POST 201 | DRF GET | Same attribution page |
| Unlink Communication | DRF POST | FastAPI GET | Link page empty |
| Re-link Communication | FastAPI POST 201 | DRF GET | Metadata link visible, Communication body not disclosed |

All scenarios use the same in-memory underlying CRM instance within each test. The test host provides an explicit `CampaignSecurityBoundary`; the `Authorization` test header is resolved only by the test's verified-principal resolver. **No claim of a real JWT/session integration is made.**

## 3. Pagination matrix

The exact same six list endpoints are compared across transports:

- `/crm/campaigns`
- `/crm/campaigns/{campaign_id}/members`
- `/crm/campaigns/{campaign_id}/audience`
- `/crm/campaigns/{campaign_id}/segment-sources`
- `/crm/campaigns/{campaign_id}/attributions`
- `/crm/campaigns/{campaign_id}/communication-links`

For each endpoint, both transport responses are compared over `limit/offset` of `1/0`, `1/1`, `200/0`, and `200/250`. Empty pages retain total/offset metadata and `has_next=false`; member pages verify `has_previous`/`has_next`. Both transports must reject `limit=0`, `limit=201`, and `offset=-1` with HTTP 422.

The existing test suite continues to validate privileged denial, 401/403 errors, and default pagination; the LOT-31-003 golden fixture protects the JSON shape and error schema separately.

## 5. Deliberate boundaries

- This lot uses **Memory** to qualify cross-HTTP/facade behavior with shared state. SQLAlchemy and Django persistence plus live PostgreSQL behavior are deferred to LOT-31-009 through LOT-31-011, in accordance with the implementation plan.
- Framework-neutral data export, failure injection at Unit of Work, and complex concurrent optimistic locking are evaluated in LOT-31-006 through LOT-31-012. Do not infer distributed exactly-once or transactional idempotency from this E2E alone.
- Privileged host scope, verified JWT/session, true multi-tenant persistence and audit security are tracked separately in the LOT-31-004/R-01 release risk register and LOT-31-014 production host reference journey.
- This lot does **not** change Campaign domain semantics, public API signatures, migrations, version metadata, current PyPI packages, or historical release tags.
