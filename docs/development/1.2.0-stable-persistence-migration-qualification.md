## CI architecture

New workflow: `.github/workflows/campaign-stable-persistence-qualification.yml`. Three jobs: Memory/SQLite and PostgreSQL 16 and 17. The PostgreSQL job deliberately uses a disposable Alembic database for SQLAlchemy/race/migration tests and creates a **different physical Django database** for native migrations and transaction tests; the final step checks the ownership boundary.

**Destructive safety:** schema reset is permitted only on the disposable CI database. Never copy the CI schema wipe or trust-auth fixture to production. `on_commit` means events are dispatched after successful transaction commit; the synchronous in-process bus is not a durable outbox, delivery retry, deduplicating broker or exactly-once guarantee. Memory's serialized UoW is not equivalent to cross-process PostgreSQL CAS.

## Design and risk decisions

- DDD, Repository and Unit of Work: preserve domain invariants at an explicit persistence boundary; controllers and host integrations do not own migrations.
- Hexagonal / Dependency Inversion: Memory, SQLAlchemy and Django are adapter implementations of the same CRM capabilities, with backend-specific transaction semantics.
- Optimistic Concurrency Control: revision CAS prevents lost writes under simultaneous PostgreSQL writers. Duplicate insert contention must not emit an uncommitted event.
- Transactional integrity: failed UoW operations leave no partially committed Campaign membership/attribution/snapshot rows.
- Separate schema ownership: a Django `django_migrations` database is not an Alembic `alembic_version` database.

**Remaining operational risks:** zero-downtime migration sequencing on real customer workloads, privileges/backup/restore, long-lived transactions, performance/RSS and production deployment recovery require separate release operations. No production database is contacted or modified by this lot.
