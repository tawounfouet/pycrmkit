## Scope and test topology

All LOT-31-009 race tests use a **real PostgreSQL** service and **distinct SQLAlchemy Sessions / UnitOfWork transactions** driven by a two-party `Barrier`. No SQLite or shared MemoryStore concurrency simulation is accepted as evidence.

The new test module is `tests/adapters/postgresql/test_campaign_concurrency_rc.py`. Its `postgres_session_factory` fixture is supplied by `tests/adapters/postgresql/conftest.py`; the session-scoped test engine creates PyCRMKit tables in a disposable CI database, and each test truncates them in isolation. **These fixtures are destructive. Do not point PYCRMKIT_TEST_POSTGRES_URL at any database containing user data.**

The standard `PostgreSQL` workflow uses PostgreSQL 17 and explicitly runs this suite. The existing `Compatibility Matrix` includes it in the `tests/adapters/postgresql` directory across PostgreSQL **16/17**, SQLAlchemy **2.0/2.1** and psycopg **3.2/3.3**.

## Test scenarios

| Gate | Real transaction scenario | Required observable outcome |
|---|---|---|
| SQL schema | Inspect PostgreSQL constraints/FKs, not merely Python ORM metadata | Unique Campaign key/direct member/snapshot, PK Campaign+Segment source, FK `ON DELETE CASCADE` |
| Campaign optimistic CAS | Two independent transactions read revision=1, barrier, attempt distinct revision=2 updates | Exactly one commit, one `campaign.revision.conflict`; persisted winner's name/metadata and revision=2 |
| Post-commit event | Both contenders stage `campaign.updated` events before racing | One event published only for the successful commit |
| Direct membership unique race | Two independent transactions insert the same direct Campaign member, synchronize before commit | One commit, one `repository.duplicate` (PG `23505`); one row and one event |
| Segment-source key race | Two independent transactions attempt same `(campaign_id, segment_id)` with one captured entity | Exactly one source, one child snapshot, one audience member, and one unique failure |
| Atomic rollback | Stage member+Segment snapshot+attribution+three events, then create a duplicate snapshot child and commit | Whole SQL transaction rolls back; 0 members/sources/snapshots/attributions, 0 published events |
| FK cascade | Commit Campaign + direct member + source + captured entity, delete Campaign via raw test SQL | No Campaign or Campaign-owned members/source/snapshot orphans |

The existing `tests/e2e/test_campaign_sqlalchemy_end_to_end.py` covers additional campaigns, duplicate attribution and timezone/JSON round-trip. The focused new module strengthens **observed transaction failure boundaries**, not just schema/unit fakes.

## Corrected adapter race edge

The `SQLAlchemyCampaignAudienceRepository.add_segment_source` method intentionally inserts and flushes the source parent before scheduling child rows. Under a genuine two-transaction race, the unique primary-key violation can happen during **`session.flush((source_model,))`**, not inside the later `UnitOfWork.commit()`.

The existing UoW translates SQLAlchemy commit errors into safe PyCRMKit errors, but previously this early flush could leak a raw `sqlalchemy.exc.IntegrityError`. The RC correction wraps **only that flush boundary** with `translate_sqlalchemy_error()`; on PostgreSQL the losing insert returns `DuplicateError` with code `repository.duplicate`, `sqlstate=23505` and safe diagnostic context (constraint/table/column if available). The original exception is chained internally, but its SQL statement/parameters are **not** placed in the public `PyCRMKitError.context`. The transaction is aborted by the context manager, with no false success or partial source.

This change does not alter Campaign public signatures, add schema migrations or introduce automatic retries. It is still incumbent on the caller to avoid logging raw chained driver exceptions with sensitive parameter values.

## Reproduction

With an **empty dedicated test** PostgreSQL instance available:

```bash
export PYCRMKIT_TEST_POSTGRES_URL="postgresql+psycopg://USER:PASSWORD@HOST:5432/pycrmkit_test"
python -m pip install -e ".[postgresql,dev]"
python -m pytest -m postgresql tests/adapters/postgresql/test_campaign_concurrency_rc.py -q
python -m pytest -m postgresql tests/e2e/test_campaign_sqlalchemy_end_to_end.py -q
ruff check tests/adapters/postgresql/test_campaign_concurrency_rc.py src/pycrmkit/storage/sqlalchemy/repositories/campaign_audience.py
```

The full `PostgreSQL` CI workflow and 8-cell compatibility matrix, not a local SQLite approximation, are the acceptance authority. The matrix logs exact resolved SQLAlchemy and psycopg versions.

## What the evidence does NOT prove

- Multi-process exactly-once or durable outbox/event replay; post-commit subscriber failure can still leave committed data.
- Serializable transactions across arbitrary host connection pools, replication lag or cross-service systems; tests exercise the PostgreSQL default transaction behavior used by the configured test database.
- An implicit database-level tenant isolation policy, nor a production JWT/session verifier. Host authorization remains outstanding at LOT-31-014.
- Reproducible latency under peak load or stable RSS; performance is LOT-31-012.
- Django ORM production schema/migration conformance, deferred to LOT-31-010.
