# PyCRMKit 1.2.0rc1 - LOT-31-010 Django Persistence & Migration Gate

**Status:** qualification candidate (exact SHA + full CI required)  
**Project:** PyCRMKit 1.2.0rc1 Campaign Production Qualification  
**Baseline:** v1.2.0b3, PR #112 draft  
**Scope:** Django ORM (Django 5.2), PostgreSQL 17 (reference integration), packaged migrations 0004 / 0005, atomicity, events and physical schema ownership.

## 1. Design contract

Django is an optional persistence adapter under the same Campaign domain facade. It does **not** define new business semantics, a new Campaign entity or a new external API. The existing domain/repository/UoW interfaces remain authoritative; ORM tables and Django migration operations remain infrastructure internals.

- Migration `0004_campaign_persistence` creates six Django-owned Campaign tables, distinct from the SQLAlchemy/Alembic layout, including `source_id` FK to the materialized snapshot source.
- Migration `0005_communication_record_store` adds the narrowly scoped Django CommunicationRecord lookup/save store. This is **not** the full CommunicationRepository protocol.
- Migration histories remain immutable. No historical `0001`–`0005` file was rewritten, and no migration is introduced by this LOT.
- The reference Django app database, isolated test database and Alembic-managed database must have **disjoint physical schema ownership**. Running both migration managers on identical physical `pycrmkit_campaign_*` tables is unsupported, even if table names match.

## 2. Qualified behavior and tests

The dedicated `tests/integrations/django/test_campaign_rc_migration_gate.py` adds deterministic checks for:

| Gate | Assertion |
|---|---|
| Migration graph & drift | `0004 -> 0005` dependency, both recorded, `makemigrations --check --dry-run`, and no `alembic_version` in Django's schema |
| Ownership | Distinct PostgreSQL database names for isolated Django contract DB and reference app DB; skip this environment-specific check outside dedicated PostgreSQL CI |
| `0005 -> 0004 -> 0005` | Communication table removed/recreated, Campaign table and seeded Campaign/Contact data preserved, migration recorder aligned |
| Cross-repository rollback | Campaign metadata, direct member, captured source/row and attribution all disappear after an injected exception; no event dispatched |
| Ambient transaction | `DjangoTransactionBridge.commit()` within outer `transaction.atomic()` is not final; outer rollback restores state and suppresses `on_commit` event |
| Constraint failure | Duplicate captured-member FK/unique row within bridge rejects the transaction and leaves no sibling writes/events |
| Attribution | `external_ref=None` normalized to `""`, duplicate blocked with domain `DuplicateError` |
| ORM cascade | Deleting one Campaign through ORM removes its children and captured members; independent CommunicationRecord table remains |
| Live PostgreSQL race | Two independent threads/connections insert identical direct Campaign member; exactly one success + one domain duplicate, one persisted logical row |
| Live FK | Database-level `source_id` FK rejects orphan captured members, not merely domain validators |

**Important:** An upgrade/downgrade path validated on a disposable isolated test database is **not** approval to downgrade production with user data. In particular, reversing migration 0005 physically drops the CommunicationRecord table and its records; reversing 0004 drops Campaign tables and their records. The production rollback procedure is restore from a tested backup or forward-only corrective migration as appropriate.

## 3. Test environment & exact commands

```bash
# Django-only smoke (SQLite for portable adapter tests; PG-only tests skipped)
python -m pip install -e ".[django,dev]"
pytest tests/integrations/django/test_campaign_rc_migration_gate.py -q

# Real PostgreSQL 17, with TWO separate databases:
# PYCRMKIT_DATABASE_URL=postgresql://.../pycrmkit_django_reference
# PYCRMKIT_DJANGO_TEST_DATABASE_URL=postgresql://.../pycrmkit_django_campaign_contracts
pytest tests/integrations/django/test_campaign_rc_migration_gate.py -q

# Run with the existing adapter/migration conformance:
pytest tests/integrations/django/test_campaign_models.py \
  tests/integrations/django/test_campaign_persistence.py \
  tests/integrations/django/test_migrations.py \
  tests/integrations/django/test_campaign_rc_migration_gate.py -q
```

In CI, `.github/workflows/django-e2e.yml` provisions PostgreSQL 17, migrates the reference app, creates a separate contract database, runs the pre-existing Django Campaign suite and the **dedicated RC1 Django Campaign Persistence and Migration Gate**, and finally proves that the reference app's schema survived. The ordinary `django.yml` continues exercising the optional Django-only/SQLite boundary.

The installed-wheel app E2E and migrations are tested separately by the existing Django PostgreSQL E2E workflow, after schema reset; a source test passing does **not** imply every installed-extras combination is qualified. The exhaustive compatibility/distribution gate is LOT-31-013.

## 4. Production operation and limitations

1. Back up production state and validate restore **before** upgrading, with rollback owner and downtime/recovery expectations written down.
2. Choose the migration manager and schema **per application**: Django migration ownership or Alembic ownership, not both. Do not run the separate reference-app and contract-test suites against one shared production DB.
3. Run Django's `migrate pycrmkit_crm`, `makemigrations pycrmkit_crm --check --dry-run`, validate recorder head `0005`, and perform actual Campaign/Communication smoke through the host's security and tenant-scoping rules.
4. Ensure tenant and identity authorization in the host: the direct Python facade and Django adapter do **not** supply universal IAM/multi-tenant isolation.
5. A post-commit event subscriber failure does **not** undo a committed database transaction; there is no durable distributed outbox promised by this RC. Inspect committed state, then reconcile through host-owned processes.
6. Verify PostgreSQL concurrency and lossless persistence semantics only within tested supported versions. The underlying PostgreSQL release-family gate is LOT-31-009; cross-adapter behavior beyond this suite belongs to LOT-31-011.
