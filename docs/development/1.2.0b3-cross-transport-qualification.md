## 1. Purpose

Prove that the two opt-in Campaign HTTP transport adapters expose equivalent semantics while delegating all business operations to the same `crm.campaigns` facade.

The primary contract test is `tests/integrations/test_campaign_transport_parity.py`. It uses one Memory-backed CRM object to compare independently serialized FastAPI (actual TestClient JSON) and DRF (rendered API response JSON) outcomes. The comparison normalizes aware timestamps to the same UTC lexical representation, but does not remove or ignore application fields.

The test deliberately checks *real* framework transport behavior, not just separate Pydantic and DRF DTO unit tests.

## 2. Contract matrix

| Contract | Shared observation | Intended evidence |
|---|---|---|
| Campaign list/retrieve | Same Campaign status, metadata, IDs, and pagination | Equal canonicalized JSON from both frameworks |
| Direct members | Same bounded page, including `has_next`/`has_previous` | Equal serialized page |
| Final audience | Same deduplicated entity reference view | Equal serialized page |
| Audience count | No inconsistent cardinality | Identical `{"count": n}` |
| Segment sources | Same captured revision, timestamps and member count | Equal serialized page |
| Attribution | Same target, source and external ref | Equal serialized page |
| Communication links | Only link metadata, never CommunicationRecord body | Equal serialized page |
| PATCH | Omitted `description` preserved; explicit null clears | Cross-framework write/read roundtrip |
| Optimistic concurrency | Stale `expected_revision` rejected | HTTP 409 on both |
| Authentication | Forged X-Actor-ID cannot establish principal | HTTP 401 on both |
| Object/action authorization | Unauthorized audience count, attributions and links are denied | HTTP 403, no totals/counts |
| Malformed request | No status mutation through PATCH | HTTP 422 on both |

Tests for CSV/JSON/JSONL import, source capture independence and portable exports are in the dedicated DataOps suites, not duplicated here.

## 3. Security requirements

- Both adapters require a trusted host-authenticated principal and a per-action/per-resource authorization policy.
- No fallback to X-Actor-ID for principal discovery; X-Actor-ID is untrusted input.
- Policies are checked before constructing the CRM facade or disclosing list totals/audience counts.
- An application cannot claim multi-tenant isolation merely by filtering results after they have been paginated.
- Full CommunicationRecord content must not be exposed through `communication-links`.

## 4. DataOps qualification and compatibility

The generic `ImportPipeline` dataclass shape and `ImportStage` enum remain unchanged, preserving the frozen v1 public API manifest. Campaign uses a specialized runner with the existing `ImportReport` and reader/exporter primitives.

The earlier DataOps head `25c4eb6c4013d767a5384c48ad63c42580c615b2` completed with 60 successful checks, 2 intentionally skipped and 4 failed. The full pytest run passed **1061 tests, 25 skips**, and the failure in the foundation job was Ruff import-order (I001) rather than an executed test assertion. That import was fixed on commit `26c8fe7181f8990c934cfe682dd815076e242dd9`, but this fact alone does not qualify any later SHA.

## 5. Qualification protocol

1. Run full `ruff check .`, `mypy`, unit/integration/compatibility suites and both optional adapter test matrices on the **same exact head SHA**.
2. Record counts and workflow/check URLs for that SHA, never mixing evidence from different commits.
3. Confirm release/public API freeze tests and core-only install remain green.
4. Confirm real PostgreSQL 17 tests, Django and Alembic migration drift, installed wheel/sdist and backend parity (LOT-30-014).
5. Only then prepare release notes/changelog and a candidate publication SHA (LOT-30-015/016).

## 6. Unresolved scope

This document does **not** certify PostgreSQL transactions, concurrent writes, filesystem-wide atomicity, or snapshot-stable exports under concurrent mutation.

Do not merge the draft PR, tag `v1.2.0b3`, publish to PyPI, or create a GitHub prerelease until the later release gates have passed.
