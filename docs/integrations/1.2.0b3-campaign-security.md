# PyCRMKit 1.2.0b3 - Campaign HTTP Security Integration Guide

**Milestone:** `1.2.0b3` (pre-release, in development)  
**Status:** Implementation example, NOT release qualification evidence  
**Related:** `1.2.0b3-http-dataops-design-freeze.md` and `1.2.0b3-campaign-http-contract.md`

## 1. Why Campaign routing is opt-in

The legacy FastAPI and DRF CRM adapters support the untrusted `X-Actor-ID` header for contextual metadata, but that header proves **nothing** about an HTTP caller's identity. Campaign HTTP is stricter: a verified principal from the host's authentication mechanism and an explicit authorization decision are required before the Campaign facade is used.

Both transports are **disabled by default**. No global authentication framework, database ACL or role hierarchy is added by this milestone.

The trust chain is:

```text
Verified host auth (JWT/session/middleware)
    -> CampaignPrincipal (validated actor ID)
    -> CampaignSecurityBoundary.require(action, campaign_id, scope)
    -> Authenticated/authorized request context
    -> CRM.with_context(actor_id=verified_id, correlation_id=bounded_trace_id)
    -> crm.campaigns.*
```

An unconfigured policy never means allow. The host must NOT use any unauthenticated header or client-supplied actor id as principal evidence.

## 2. FastAPI integration

Imports (only available with the optional FastAPI dependencies):

```python
from pycrmkit.integrations.campaign_security import (
    CampaignPrincipal,
    CampaignSecurityBoundary,
)
from pycrmkit.integrations.fastapi.campaign_security import CampaignHTTPAccess
from pycrmkit.integrations.fastapi.router import create_crm_router
```

Use a **trusted host authentication implementation** to populate the principal. For example, a previously authenticated middleware can set a server-verified user on `request.state`. Do not set it from an unverified HTTP field.

```python
def from_trusted_host_auth(request):
    verified_user = getattr(request.state, "verified_user", None)
    if verified_user is None:
        return None
    return CampaignPrincipal(actor_id=str(verified_user.id))


def authorize_campaign(principal, *, action, campaign_id, scope):
    # Delegates to the application's REAL policy/IAM engine.
    # This is intentionally illustrative and not a permissive policy.
    return host_policy_engine.check(
        principal.actor_id,
        action=action,
        campaign_id=campaign_id,
        scope=scope,
    )


boundary = CampaignSecurityBoundary(
    resolve_principal=from_trusted_host_auth,
    authorize=authorize_campaign,
)

access = CampaignHTTPAccess(
    factory=build_crm_for_request,
    security=boundary,
)
app.include_router(
    create_crm_router(build_crm_for_request, campaign_access=access),
    prefix="/crm",
)
```

The code above assumes `host_policy_engine`, `build_crm_for_request` and trusted middleware are provided by the host. It does **not** implement JWT validation or a working policy on its own.

Without `campaign_access`, `create_crm_router(factory)` retains the existing routes and does not register Campaign.

## 3. Django REST Framework integration

Set `PYCRMKIT_CRM_FACTORY` as usual and provide an explicit security boundary:

```python
from pycrmkit.integrations.campaign_security import CampaignSecurityBoundary
from pycrmkit.integrations.django.drf.campaign_security import (
    authenticated_drf_principal,
)

PYCRMKIT_CAMPAIGN_SECURITY = CampaignSecurityBoundary(
    resolve_principal=authenticated_drf_principal,
    authorize=authorize_campaign,  # Host-specific policy function
)
```

`authenticated_drf_principal` reads the identity provided by the configured DRF authentication classes through `request.user`. It rejects anonymous users and users without a persistent ID. The host MUST configure real DRF authentication and the policy implementation; a public `X-Actor-ID` is not authentication.

Register the routes explicitly:

```python
router = create_drf_router(include_campaigns=True)
```

If `PYCRMKIT_CAMPAIGN_SECURITY` is missing, misconfigured, or not an instance of `CampaignSecurityBoundary`, DRF route assembly fails with `ImproperlyConfigured`.

## 4. Authorization actions and sensitive data

| Action | Scope |
|---|---|
| `campaign.create` | create permission, host-owned context |
| `campaign.list` | entire requested list scope, including status/owner/archived/page |
| `campaign.read` | one Campaign id |
| `campaign.update` | one Campaign id, metadata mutation |
| `campaign.lifecycle` | one Campaign id, activate/complete/archive |
| `campaign.members.read` | direct members + deduplicated audience/count |
| `campaign.members.write` | direct members |
| `campaign.sources.read` / `write` | Segment source/snapshot metadata |
| `campaign.attribution.read` / `write` | attribution references |
| `campaign.communications.link` | link metadata and real record-existence checking |
| `campaign.communications.content.read` | **not enabled** in the initial HTTP registry |
| `campaign.data.import` / `export` | future or explicit Python DataOps boundary |

A list-level policy must authorize the **complete candidate scope**. A list filtered after fetching from a shared repository can expose cross-tenant `total` and must not be used. If the host cannot prove the result set belongs to the authorized scope, it must **deny list/search** rather than post-filter.

No full communication content is included in the initial b3 HTTP endpoints; those contain potentially sensitive CRM data and need a separate, audited permission.

## 5. Security checks

Before production exposure, verify all of these on both transports:

1. Without verified principal, `X-Actor-ID: admin` still returns HTTP 401.
2. With authenticated principal but denied action or Campaign, return HTTP 403 **before** invoking CRM.
3. Authenticated actor in audit/domain context matches the verified host actor, not the header.
4. GET list and audience count never disclose unauthorized entity cardinalities.
5. No unbounded JSON metadata, bulk size or pagination.
6. Invalid/untrusted `X-Correlation-ID` is replaced by a server generated value.
7. Request-boundary failures do not leak tokens, PII, SQL, or stack traces.
8. Explicit application policy, integration identity providers, migrations, PostgreSQL and wheel/sdist tests remain separate qualifications.

**Implementation note:** The existing non-Campaign bridges retain their original compatibility behavior; this document does not imply every legacy REST route has been migrated to this newer security boundary. The b3 security requirement applies to **Campaign HTTP**.

## 6. Release discipline

A test module or a draft PR is **not** a production qualification certificate. Tagging, merging, PyPI publication, and GitHub prerelease promotion require the later b3 qualification gates, exact source SHA and checked build artefacts.
