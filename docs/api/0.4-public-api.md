# PyCRMKit 0.4 Public API

`0.4.0` promotes the qualified Communication surface to stable for the
`0.4.x` release line.

## Compatibility with 0.1–0.3

The shallow root imports remain unchanged:

```python
from pycrmkit import CRM, CRMConfig, CRMContext, __version__
```

All stable CRM Core, Activity/Task/Timeline and Sales facade namespaces remain
available.

## Stable additive 0.4 facade surface

```text
CRM.email

crm.email.send
crm.email.record_delivery_event
crm.email.get
crm.email.for_contact
crm.email.for_organization
crm.email.delivery_history
```

`CRM.memory(...)` accepts optional `email_provider`, `email_sender`, and
`template_renderer` dependencies. `CRM.with_context(...)` preserves them.

## Provider-neutral contracts

The stable Communication domain separates:

```text
CommunicationIntent
DeliveryAttempt
CommunicationRecord
EmailDeliveryEvent
```

Email transport uses `EmailMessage`, `EmailProvider.send(...)`,
`EmailProviderResult`, and `EmailDeliveryService`. Provider acceptance means
transport acceptance only, not mailbox delivery.

## Templates and providers

Jinja2 is optional through `pycrmkit[email]`. SMTP is implemented with the
Python standard library. Resend remains optional through `pycrmkit[resend]`.

```python
from pycrmkit.providers.email import SMTPConfig, SMTPEmailProvider, SMTPSecurity
from pycrmkit.providers.email.resend import ResendConfig, ResendEmailProvider
```

## Stable lifecycle events

```text
email.queued
email.sent
email.delivered
email.opened
email.clicked
email.bounced
email.failed
```

Not every provider is required to produce every downstream event. Provider
callbacks correlate through provider name/message ID; external event IDs provide
idempotent replay when supplied.

## Communication history

Delivery history is append-only. Out-of-order callbacks remain in history but
do not regress the current `CommunicationRecord.delivery_status`.

## Timeline architecture decision

Communication is its own bounded context and source of truth. Stable `0.4.x`
projects meaningful Communication lifecycle events directly into Timeline as
`TimelineEntryKind.COMMUNICATION`.

PyCRMKit deliberately does **not** create a duplicate `Activity(type="email")`
for the same communication. Activity and Communication remain separate source
domains that converge in the Timeline read model.

## Privacy and persistence boundaries

Event payloads and Timeline metadata expose lifecycle/provider context, not
recipient addresses or message bodies. `0.4.x` qualifies Memory persistence;
SQLAlchemy/PostgreSQL remains scheduled for `0.6.x`.

## Compatibility policy

This documented surface is compatibility-governed for `0.4.x`. Durable
webhooks/event delivery begin in `0.5.x`.
