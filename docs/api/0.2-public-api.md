# PyCRMKit 0.2 Candidate Public API

`0.2.0rc1` freezes the candidate Activity & Timeline surface that is intended to become stable in `0.2.0` if no release-blocking compatibility defect is found.

## Compatibility with 0.1

The root imports stay unchanged:

```python
from pycrmkit import CRM, CRMConfig, CRMContext, __version__
```

`pycrmkit.__all__` remains:

```text
CRM
CRMConfig
CRMContext
__version__
```

The `0.1` CRM Core namespaces continue to be available without renaming.

## Additive 0.2 facade surface

```text
CRM.activities
CRM.tasks
CRM.timeline
```

`crm.activities` provides interaction logging, reads, typed updates and portable listing.

`crm.tasks` provides create/read/update/list plus explicit lifecycle transitions:

```text
start
complete
cancel
reopen
```

Lifecycle status remains protected from generic patches.

`crm.timeline` is intentionally read-only at the facade boundary:

```text
get
for_contact
for_organization
```

Application code does not append or mutate Timeline entries directly through the facade.

## Timeline contract

Timeline is a derived customer/relationship-history read model sourced from meaningful Activity and Task lifecycle events. Projection participates in the same Unit of Work as the source mutation.

Qualified semantics include:

- immutable projected entries;
- idempotent replay keyed by the source event identity;
- conflicting replay rejection;
- reverse chronological ordering by business occurrence time, then kind and id;
- exact offset pagination;
- half-open time windows `[occurred_from, occurred_until)`;
- Contact and Organization reference filtering;
- imported historical Activity timestamps independent of ingestion time;
- projection rollback when the source transaction rolls back;
- public EventBus delivery only after commit.

## Activity contract

Activities retain a distinct `occurred_at`, allowing historical interactions to be ingested without rewriting their business time. Participants and related CRM entities use generic `EntityReference` values and do not require aggregate hydration.

## Task contract

Task status changes use explicit transitions. The candidate lifecycle states are:

```text
open
in_progress
completed
cancelled
```

Reopening a terminal task starts a fresh open work cycle and resets lifecycle completion timestamps according to the aggregate contract.

## Candidate runtime matrix

The RC is qualified by GitHub Actions on the project's supported Python matrix, currently Python 3.11, 3.12 and 3.13.

## Still deferred

The following remain outside the `0.2` candidate compatibility promise:

- SQLAlchemy/PostgreSQL persistence;
- Django/FastAPI adapters;
- Sales/Pipeline domains;
- durable event delivery / transactional outbox;
- webhooks;
- asynchronous projection workers;
- cursor pagination and external search indexes.
