# PyCRMKit 0.3 Public API — Release Candidate

`0.3.0rc1` freezes the candidate Sales Foundation surface that is intended to
be promoted unchanged to `0.3.0` stable.

## Compatibility with 0.1 and 0.2

The shallow root imports remain unchanged:

```python
from pycrmkit import CRM, CRMConfig, CRMContext, __version__
```

`pycrmkit.__all__` remains:

```text
CRM
CRMConfig
CRMContext
__version__
```

All stable `0.1` CRM Core and `0.2` Activity/Task/Timeline facade namespaces
remain available.

## Candidate additive 0.3 facade surface

```text
CRM.leads
CRM.opportunities
CRM.pipelines
```

The candidate method surface is deliberately narrow:

```text
crm.leads.create
crm.leads.qualify
crm.leads.disqualify
crm.leads.convert

crm.opportunities.create
crm.opportunities.move

crm.pipelines.define
crm.pipelines.get
crm.pipelines.list
```

Lead and Opportunity repository/service read APIs exist below the facade, but
`crm.leads.get/list` and `crm.opportunities.get/list` are not part of the
candidate public facade.

## Lead contract

Lead lifecycle states are:

```text
new
open
contacted
qualified
disqualified
converted
```

The public facade exposes capture, qualification, disqualification and
Lead-to-Opportunity conversion. Conversion requires a qualified Lead.

## Conversion contract

`crm.leads.convert(...)` coordinates Lead and Opportunity persistence in one
Unit of Work.

Qualified semantics include:

- Contact and optional Organization identity are inherited by the Opportunity;
- a supplied Pipeline initializes the Opportunity at its initial Stage;
- initial Stage default probability is applied;
- the Lead becomes terminally `converted`;
- conversion provenance links the Lead to exactly one Opportunity;
- equivalent retries with the same idempotency key return the same Opportunity;
- conflicting reuse of the same key raises a typed conflict;
- a different key cannot convert an already converted Lead again;
- audit state commits atomically with the domain mutation;
- external in-process event handlers execute after commit.

## Opportunity and Pipeline contract

Pipeline definitions provide ordered Stages, allowed transitions, default
probabilities and terminal outcomes.

`crm.opportunities.move(...)`:

- rejects undeclared transitions;
- prevents exiting terminal Stages;
- records `stage_entered_at`;
- adopts the target Stage default probability;
- maps terminal Stage outcomes to Opportunity status;
- emits normalized stage/outcome events after commit.

Public won/lost outcomes are reached through configured terminal Stages rather
than direct facade `mark_won` / `mark_lost` methods.

## Candidate Sales events

The `0.3` RC qualifies:

```text
lead.created
lead.qualified
lead.disqualified
lead.converted
opportunity.created
opportunity.stage_changed
opportunity.won
opportunity.lost
```

`pipeline.created` is also emitted by pipeline definition.

Events preserve actor/correlation context supplied through
`crm.with_context(...)`. Audit remains separate system mutation history.

## Qualified release scenario

The release candidate verifies the intended stable sequence:

```text
create Lead
    ↓
qualify
    ↓
convert
    ↓
Opportunity in initial Pipeline Stage
    ↓
reject invalid transition
    ↓
advance through allowed Stages
    ↓
Won
```

It also qualifies disqualified Lead and lost Opportunity terminal outcomes.

## Still deferred

The following are outside the `0.3.x` compatibility promise:

- Sales event projection into Timeline;
- SQLAlchemy/PostgreSQL persistence;
- durable transactional outbox and event-delivery retry;
- webhook delivery;
- FastAPI and Django integrations;
- communication/email capabilities;
- import/export/deduplication;
- analytics and AI extensions.
